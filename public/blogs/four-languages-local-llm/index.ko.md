# 로컬 1.8B 모델을 번역가로 삼아 4개 국어 블로그 출시하기

이 블로그는 중국어만 있어서 좋지 않다.

그래서 시간이 나는 동안 English, 日本語, 한국어를 모두 올렸다. 전체 과정에서 번역 작업은 대부분 1.8B 크기의 로컬 번역 소형 모델에 맡겼고, 나는 교정과 버그 수정만 담당했다. 이 글은 전체적인 리뷰로, 아키텍처를 어떻게 선택했는지, 번역 파이프라인을 어떻게 구축했는지, 그리고 실제로 서비스에 배포될 때 겪게 되는 몇 가지 문제들에 대해 다룬다.

## 먼저 결론부터 말하자면

- 전 사이트 UI 문구 464건 × 3개 언어, 방문자 측과 관리자 측 모두에 적용 (글 작성 후면, 사이트 설정 팝업 등도 포함)
- 13개 글 전체 번역 × 3개 언어 = 39개 번역본, 더불어 페이지, 친구 링크, 프로젝트, 이미지, 문장에 관련된 데이터 변형도 포함
- 총 5개의 제출물, 319개의 파일 변경
- 왼쪽 하단 언어 메뉴를 전환하여 영구적 설정을 선택하면, <html lang>도 함께 변경됨

효과가 어떤지, 언어를 바꿔서 여기저기 클릭해보면 알 수 있습니다.

## 왜 next-intl을 사용하지 않나요?

Liuxiandong과 같은 성숙한 솔루션을 사용할 생각으로 신중히 고려했지만 결국 포기했습니다. 그 이유는 우리 블로그의 형태가 너무 특이적이기 때문입니다: 글의 본문은 GitHub 저장소에（`public/blogs/<slug>/index.md`）저장되어 있으며, 실행 시 fetch하여 렌더링합니다. 이는 마치 "GitHub이 바로 데이터베이스다"는 것과 같습니다. 이러한 클라이언트 렌더링 + 정적 데이터 파일의 아키텍처에서는 locale 라우팅을 사용하는 것은 단지 자신을 귀찮게 하는 것에 불과합니다.

마지막으로 가장 가벼운 방안을 선택했습니다: 자체 사전 구축 + React Context + localStorage의 영구 저장 방식을 사용하며, 사이트에 이미 있는 글꼴 전환 메커니즘과 완벽하게 동기화됩니다. 핵심은 단 세 개의 파일뿐입니다:

- `config.ts`: 언어 코드 등록표, 표시 이름, `htmlLang` 매핑
- `translate.ts`: 두 단계 사전 값 조회, key가 부족하면 자동으로 중국어로 돌아감, 절대 화면이 검게 변하지 않음
- `locales.ts`: 각 언어 사전의 등록入口

한 가지 중요한 선택에 대해 솔직하게 말하자면: 영문 모드에서는 URL을 변경하지 않고 `/en/` 라우트도 없습니다. 이는 SEO 측면에서 불이익입니다. 개인 블로그는 이 점에 별로 신경 쓰지 않지만, 상업적 사이트라면 신중하게 생각해야 합니다.

내용 파일은 «변형 확장자» 규칙을 따릅니다: `index.en.md`, `index.ja.json`, `list.ko.json`…… 실행 시 현재 언어 버전을 우선적으로 로드하며, 파일이 없으면 중국어 원본으로 돌아갑니다. 따라서 언제든지 일부 번역본만 업로드되어도 사이트는 완전합니다.

## 번역가는 누구인가

현지에서 OpenAI와 호환되는 추론 서비스를 만들었으며, 두 가지 모델을 추가했습니다.

- 主力：**Hy-MT2-1.8B**, 텐센트의 혼원 번역 전용 모델, 4bit quantization. 번역 전용 소규모 모델로 빠르고 안정적입니다.
- 備胎：Qwen3.8-27B, 특정 언어나 단일 문서에 만족하지 못할 경우 이 모델로 바꿔 다시 실행합니다.

지시어의 설계는 몰입형 번역 플러그인을 참고했습니다: 오직 번역 결과만 출력해야 하며, 단락 수는 일치해야 하며, 여러 단락은 `%%`로 구분해야 합니다. 마지막 항목은 매우 중요합니다—글을 빈 줄로 나누어 연속된 단락으로 구성하고(각 배치 최대 4단락), 한 번에 한 배치를 번역하여 `%%`로 분리해 배치해야 합니다. 배치가 많을수록 단락이 어긋나는 경우가 발생하기 쉬우니 몰입형 번역이 기본적으로 4단락을 사용하는 것은 타당합니다. 실험해 보니 초과되면 단락이 사라지기 시작합니다.

파이프라인 스크립트는 총 6개의 파일로 구성되며, 2개의 인터페이스가 있습니다:

- `i18n:dict`: UI 다중언어 사전 (zh 영역 파일 → en/ja/ko 영역 파일)
- `i18n:content`: 콘텐츠 번역 (마크다운 글, 설정 파일, 다양한 인덱스 JSON)

구역 코드 블록은 전체적으로 건너뛰고 번역하지 않으며, frontmatter도 번역하지 않습니다. 전체 번역 실패 시 단계별 번역으로 자동 전환되며, 단일 단계 번역 실패 시 중국어를 그대로 유지합니다 – 구조는 항상 일치하며, 최악의 경우는 그 한 문장만 번역되지 않는 것입니다.

또한 디자인이 나머지 모든 문제를 해결해줍니다: **증분 의미론, 재실행 시 덮어쓰지 않음**. 사전 파일에 이미 있는 번역문(중국어가 아닌 내용)은 그대로 유지하고, 새로 추가된 key만 번역합니다; 콘텐츠 파일은 `--skip-existing`를 사용하여 이미 있는 번역문은 건너뛰습니다. 이렇게 하면 "한 문장을 수정 → 한 번 실행 → 한 문장을 교정"의 순환이 가능해지며, 그렇지 않으면 매번 재실행 시 인간이 교정한 내용이 무시되어 누구도 해결할 수 없습니다.

간단히 프로젝트 세부 사항을 말하자면, 생성기에서 출력되는 문자열의 문자열 값은 저장소의 prettier 스타일과 정렬되어 있습니다 (기본적으로 single quotes를 사용하며, 내용에 single quotes가 포함되면 double quotes로 감싸집니다). zero diff를 다시 실행하면 git에서 형식적인 오류가 발생하지 않습니다.

## 다중 지능체 분업

문구 추출과 같은 작업은 양이 많지만 패턴이 고정되어 있어 다중 지능체의 병렬 작업에 가장 적합합니다. 방문자 측에는 4개의 agent이 분야별 개조를 담당합니다 (블로그, 음악, 콘텐츠 집합, 도구 상자), 관리 측에도 4개가 있습니다 (작문 백엔드, 설정 팝업, 관리 도구 모음, 대화상자 및 toast). 마지막 2개는 감사 agent으로, 하나는 데이터의 완전성을 확인하고 다른 하나는 locale 인지 누락을 확인합니다.

시작 전에 규범을 확정합니다: 사전은 비즈니스 영역별로 파일을 분리하고, key 명명 규칙, en 디렉터리는 변경 금지 (번역 파이프라인에 남겨두기 위해), 참고 실제를 먼저 실행합니다 (저는 먼저 4개의 파일을 수정하여 샘플로 사용합니다). 이렇게 하면 agent들 사이에 충돌이 발생하지 않고, 결과물은 바로 사용할 수 있습니다.

## 출시 후 겪은 실수들

### 1. 월요일이 "One"으로 표기됨

중국어 요일 목록 `['一','二','三',...]`을 모델에 입력한 후, 영문 버전으로 돌아온 것은:

> One / Two / Three / 4 / 5 / 6 / Day

처음 세 개는 대문자 숫자로 해석되며, 중간 세 개는 아랍어 숫자를 정직하게 변환했고, 마지막 '일'은 정확하게 변환되었습니다. 일본판은 더욱 독특하여 일차부터 삼차까지 원래 그대로 유지됩니다—결국 일본어에서는 실제로 숫자로 사용될 수 있기 때문입니다.

수정 방법은 매우 간단합니다: 수동으로 다시 작성합니다. Mon/Tue/Wed, 월화수목금토일, 월화수목금토일. 교훈은 **문맥과 분리된 짧은 태그는 번역기의 첫 번째 적입니다**: 요일, 단위(「시/분/초」가 Hour/Minute 단수로 변환됨), 버튼(「변환」이 Converting 현재형으로 변환됨) 등 이런 종류는 반드시 수동 처리해야 합니다.

### 2. 문장 속에 박혀 있는 파편을 변환할 수 없음

Wuthering Waves의 카드 분석 페이지에 사용 가이드가 있습니다, «F12를 클릭하고 오른쪽 Network 패널을 클릭하세요»—F12와 Network는 JSX 내에서 강조된 <span>입니다, 전체 문장이 사전에 분리된 앞뒤 부분으로 존재합니다. 모델이 이런 파편을 변환할 때는 전후 문맥이 전혀 없으며, 한국어에서는 더욱 큰 문제입니다:助词이 이전 단어에 붙어 있어 분리된 구조를 다시 결합할 수 없습니다.

단어 단위로 대응하는 것을 포기하고 슬롯 위치에 맞춰 전체 문장의 구조를 다시 쓰는 방법으로, 세 가지 언어 각각에 자신들의 순서에 맞는 버전을 하나씩 작성합니다. 이는 국제화 문안 디자인의 첫 번째 수업입니다: **전체 문장을 번역기에게 맡기세요, 조각난 부분을 주지 마세요.**

### 3. 용어 이동

13개 글의 태그는 각각 독립적으로 번역되었으며, 같은 'Liuxiandong'은 두 가지 버전으로 번역되었고, 'pretext'는 의미에 맞게 '배경'으로, 인터넷의 'agent'은 '대리점'으로 번역되었으며, 한국어판 '명조'의 공식 이름은 글자를 잘못 썼습니다. 마지막으로 스크립트를 작성하여 중문 원문과 비교하며 항목별로 수정하여 세 가지 언어의 용어표를 맞춘습니다.

올바른 방식은 번역하기 전에 용어표를 제공하거나, 번역을 마친 후 일련 과정을 거쳐 일관성을 맞추는 것입니다. 고유명사에 대해서는 모델이 스스로 일관성을 유지할 것이라고 기대하지 마세요.

### 4. `useState(props)`：카드가 언어 전환과 함께 동작하지 않음

가장 은폐된 경우입니다. Suni의 카드 컴포넌트에 이런 줄이 있습니다:

```ts
const [localBlogger, setLocalBlogger] = useState(blogger)
```

state는 prop을 설정할 때 단 한 번만 복사됩니다. 언어를 전환하면 목록 데이터가 변하지만 key는 변하지 않고 컴포넌트가 재생성되지 않으며, 카드 내부는 처음 페이지에 들어왔을 때의 언어로 유지됩니다. 당시의 현상은 매우 이상했습니다: React fiber 내에서 props는 이미 일본어였고, 화면에는 여전히 중국어가 있었으며, console에는 아무런 메시지도 없었습니다.

법을 수정하는 한 줄: 목록에 `key={locale}`를 추가하여 강제로 재구축합니다. 교훈: **"props로 초기화된 state"는 prop의 변화에 반응하지 않습니다**, 언어나 주제와 같은 전역 컨텍스트에서 이를 피하는 것이 가장 중요합니다.

### 5. 다국어는 단순한 번역이 아닌 데이터 일관성입니다

세 가지 연쇄적인 문제가 모두 "저장" 측에 있습니다:

- 편집 및 저장 과정에서 현재 언어의 병합 보기가 사용된다면, 일본어 모드에서 한 번 저장하면 일본 제목이 중문 `index.json`에 저장됩니다—데이터 소스가 번역본에 오염됩니다.
- 글 삭제 시 중문 인덱스만 삭제되고, 영일한 인덱스에는 남은 고아 항목이 남아 있어 해당 언어로 이동하면 404 오류가 발생합니다. 이가 바로 사용자가 말하는 "프론트엔드에서 때때로 오류가 발생하는" 진짜 원인입니다.
- 일본어에서 7개 글의 분류는 "요약"이지만, 분류 목록에는 "まとめ"라고 되어 있습니다. 같은 의미에 두 가지 번역이 있어 그룹 분류가 제대로 되지 않습니다.

**翻译解决「显示」，解决不了「写入」。凡是往数据源写的链路，都必须钉死在源语言上。**

## 품질이 과연 괜찮은가

솔직히 두 등급으로 나눌 수 있어요:

**글 내용: 예상보다 훨씬 좋습니다.** Markdown 구조, 이미지 경로, 인라인 코드가 모두 유지되어 있고 문장도 자연스럽으며, 한국어 존경문체도 일관되어 있습니다. 1.8B 크기의 작은 모델은 글을 쓸 수는 없지만, 글을 읽는 것은 충분히 가능합니다.

**UI 단어: 인력 교정이 필요합니다.** 464개 중 약 10%가 문제가 있지만, 이는 예상 가능한 범주(주, 단위, 시제, 용어)에 해당하므로 목록을 따라서 확인하면 됩니다.

## 현재 새로운 언어를 추가하는 데 얼마나 시간이 걸리나

아키텍처의 모든 매개변수가 파라미터화된 후에는 세 단계만 남았습니다:

```ts
// 1. 언어 코드와 표시 이름을 등록합니다
const LOCALES = ['zh', 'en', 'ja', 'ko', 'fr']
```

```bash
# 2. 번역 파이프라인을 실행하여 로컬 모델을 완전 자동으로 번역
TRANSLATE_TARGET=fr pnpm i18n:dict
TRANSLATE_TARGET=fr pnpm i18n:content
```

3. 날짜 형식을 추가하여 고위험 항목(일자, 단위, 튜토리얼 구조)을 인력으로 교정할 수 있도록 한다.

기계 시간으로 20분, 인력 시간으로 30분. 향후 새 글을 작성할 때 번역을 고민할 필요가 없으며, `pnpm i18n:content --skip-existing`를 사용하여 부족한 언어 버전을增量적으로 번역하면 충분하다.
