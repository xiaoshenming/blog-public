# ローカル 1.8B モデルを翻訳官にして、四言語ブログをリリースした話

这个博客只有中文，不好。

于是趁着有空，一口气把 English、日本語、한국어 全上了。整个过程中，翻译工作基本都交给了本地一个 1.8B 的翻译小模型，我只负责校对和修 bug。这篇文章是完整复盘：架构怎么选、翻译管线怎么搭、以及几个只有真正上线才会踩到的坑。

## 先说结论

- 全サイトのUIコンテンツ 464件 × 3か国語、訪問者側と管理側の両方をカバー（作成バックドア、サイト設定ポップアップなども含む）
- 13つの記事全文 × 3か国語 = 39つの翻訳文、さらにページ、友链接、プロジェクト、画像、文章に関するデータのバリエーションも含む
- 合計5件の提出、319件のファイル変更
- 左下の言語メニューを切り替え、`<html lang>`が自動で変更される

効果はどうか、言語を切り替えてどこにポチポチを押せばわかる。

## なぜ next-intl を使わないのか

Liuxiandongについては next-intlのような成熟したソリューションを真剣に検討したが、最終的に諦めた。その理由は、私たちのブログの構造が非常に特殊だからである：記事本文はGitHubリポジトリ内の`public/blogs/<slug>/index.md`に存在し、実行時にfetchしてレンダリングされるため、まるで「GitHubがデータベースである」ような状態になる。このようなクライアントレンダリング＋静的データファイルのアーキテクチャでは、localeルーチンを使用するのは単に手間をかけるだけだ。

最後に最も軽い方案を選んだ：自作辞書 + React Context + localStorageの持久化処理を採用し、サイト内に既存のフォント切替え機構と完全に同構造である。核心は3つのファイルだけだ：

- `config.ts`：言語コード登録表、表示名、`htmlLang`のマッピング
- `translate.ts`：二層辞書の値取得、keyが欠落時は自動的に中国語に戻り、画面が白黒になることはない
- `locales.ts`：各言語辞書の登録入口

重要な選択について正直に言うと、英語モードではURLを変更せず、`/en/`のルートもないため、SEO面で不利になる。個人ブログの場合はこの点は問題ないが、商業サイトとしてはよく考えるべきだ。

コンテンツファイルには「バリアントサフィックス」の規定を適用する：`index.en.md`、`index.ja.json`、`list.ko.json`……実行時には現在の言語バージョンを優先的に読み込み、ファイルが存在しない場合は中国語の原文に戻る。したがって、いつでも一部の翻訳ファイルのみをアップロードしても、サイトは完全な状態を保つことができる。

## 翻訳官は誰ですか

現地でOpenAI互換の推論サービスを立ち上げ、2つのモデルを使用している

- 主力：**Hy-MT2-1.8B**、Tencentの混元翻訳専用モデル、4bit量化。翻訳専用の小さなモデルによる干渉翻訳で、速くて安定している
- 備胎：Qwen3.8-27B、特定言語や単文が満足できない場合に使用し、再実行する

提示词の設計は没入型翻訳プラグインを参考にした。译文のみを出力し、段落数は一致させる必要がある。複数段落は `%%` で区切る。最後の項目は重要だ——文章を空行で分割し、隣接する段落を一括にする（各一括に最大4段落）。一度に一括を要求し、`%%` で分割して適切な位置に配置する。一括が多いほど段落の不整合が生じやすい。没入型翻訳のデフォルトである4段落は理にかなっている。実験で4段落を超えた場合は段落が失われる。

ラインスクリプトには合計6つのファイルがあり、2つの入力があります：

- `i18n:dict`：UI用辞語辞書（zh域ファイル → en/ja/ko域ファイル）
- `i18n:content`：内容（記事のMarkdown、config、各種索引JSON）

囲みコードブロックは全てスキップし、frontmatterもスキップします。バッチ翻訳が失敗した場合は自動的に段落ごと翻訳に切り替わり、さらに段落が失敗した場合は中国語のまま保持されます。構造は常に一致しており、最悪の場合はその一節だけが翻訳されないだけです。

また、デザインが後続のすべてを救っています：**インクリメンタルセマンティクス、再実行でコピーしない**。辞書ファイル内の既存の翻訳（中国語以外の内容）はそのまま保持し、新規追加されたkeyのみを翻訳します。内容ファイルには `--skip-existing`を付けており、既存の翻訳は直接スキップされます。このように「一つの文案を変更 → 一度実行 → 一節を校正」というサイクルが成立すれば、そうでなければ毎回の再実行で手作業の校正が消えてしまい、誰も救えません。

工程の詳細として、生成器が出力する文字列の字面量は倉庫の prettierスタイルに合わせられている（デフォルトでは単一の引用符が使用され、内容に引用符が含まれる場合のみ二重引用符で囲まれる）。gitではフォーマットのノイズが発生しない。

## 多主体の分担

文案抽出という作業は量が多いがパターンは固定されているため、多主体の並行処理に最適である。訪問者側には4つのagentが配置され、各々が異なる分野を改造する（ブログ、音楽、コンテンツ集合、ツールキット）。管理側にも4つが配置され（ライティングバックエンド、設定ダイアログ、管理ツールバー、ダイアログとtoast）、最後に2つは監査agentで、1つはデータの完全性をチェックし、もう1つはlocaleの認識漏れをチェックする。

開始前に規範を明確にする：辞書は業務領域に応じてファイルを分割し、keyの命名規則、enディレクトリは変更禁止（翻訳ライン用に残す）、実装例を参考に先に行う（私が4つのファイルを先に修正してサンプルとする）。これによりagent間の衝突がなく、出力物は直接使用可能になる。

## リリース後に発見した問題点

### 1. 月曜日が "One" と翻訳される

中国の曜日リスト `['一','二','三',...]` をモデルに渡し、英語版が戻ってきた内容は：

> One / Two / Three / 4 / 5 / 6 / Day

最初の3つは大文字の数字として理解されており、中間の3つはアラビア数字を正直に翻訳しているが、最後の「日」は正しく翻訳されている。日本語版はさらに驚くべきことで、一、二、三は元のまま保持されている——結局のところ日本語ではそれらが実際に数字として使われるからだ。

修正方法は非常に簡単：手作業で書き直す。Mon/Tue/Wed、月火水木金土日、월화수목금토일。教訓は**文脈から切り離された短いタグは翻訳器の天敵である**：曜日、単位（「時/分/秒」が Hour/Minuteの単数形に翻訳される）、ボタン（「转换」が进行时 Convertingに翻訳される）、この種類は手作業で対処する必要がある。

### 2. 文の中に埋め込まれた断片は翻訳できない

Wuthering Wavesのカード分析ページには使用マニュアルがあり、「F12をクリックし、右側の Networkパネルをクリック」とある——F12とNetworkはJSX内で強調された`<span>`であり、文全体が前後の断片に分かれて辞書に保存されている。モデルをこの種の断片を翻訳する際は、前後の文が全く存在しないため、韓語ではさらに困難である：助詞が前の単語に付着しており、分割された骨格は元に戻すことができない。

単語一つ一つに対応するのをやめ、スロットの構造に基づいて全文の骨格を書き直す。3つの言語それぞれに、自分の語順に合ったバージョンを1つずつ書く。これが国際化コンテンツデザインの最初のレッスンです：**完全な文を翻訳器に任せて、断片にしないこと。**

### 3. 用語の異なる解釈

13つの記事のタグはそれぞれ独立して翻訳されており、同じ「Liuxiandong」は2つのバージョンが出てきました。「pretext」は「背景」と意訳され、「ネットワークの代理」は「代理商」と翻訳され、韓語版「Wuthering Waves」の公式名「명조」は文字が間違っています。最後にスクリプトを使って中国語の原文と照合し、3つの言語の用語表を一致させます。

正しいやり方は、翻訳前に用語表を提供すること、または翻訳後に一通りの一致チェックを行うことです。固有名詞については、モデルが自動的に統一されることを期待してはいけません。

### 4. `useState(props)`：カードが言語切替えに連携しない

最も隠蔽的な例です。Suniのカードコンポーネントには次の行があります：

```ts
const [localBlogger, setLocalBlogger] = useState(blogger)
```

stateはプロパティの初期化時に一度コピーされます。言語を切り替えた後、リストデータは変わりますが、keyは変わらず、コンポーネントも再インスタンス化されません。カード内部には最初にページに入った時の言語が保持されます。当時の現象は非常に奇妙でした：React fiber内ではプロパティが日本語であり、画面にはまだ中国語が表示され、consoleには何も表示されませんでした。

修法一行：リストに `key={locale}` を追加して強制的に再構築する。教訓：**「props から初期化される state」は自然と prop の変化に反応しない**、言語やテーマなどのグローバルなコンテキストが最も問題になる。

### 5. 多言語は単なる翻訳ではなく、データの一貫性が重要

3つの問題点はすべて「書き出し」の側にあり：

- 編集保存のプロセスが「現在の言語のマージビュー」を使用している場合、日本語モードで一度保存すると、日本語のタイトルが中国語の `index.json` に書き込まれる——データソースが翻訳に影響される
- 記事の削除は中国語の索引のみを削除し、英語・日本語・韓語の索引には孤立した記事が残り、それらの言語で開くと404エラーが発生する。これがユーザーが報告する「フロントエンドで時々エラーが発生する」の本当の原因である
- 日本語の場合、7つの記事の分類は「要約」であるが、分類リストでは「まとめ」と呼ばれている。同じ意味を持つが2つの異なる訳名が使われており、グループ分けが正確に行われていない

**「表示」の解決は「書き込み」にはできない。データソースに書き込むすべてのリンクは、元言語に固定されなければならない。**

### エンブレム：言語ボタンが画面から飛び出す

新しく作った左下の言語ボタンは `card.base` のスタイルを使用している——これはホームページでの自由なドラッグカード用で、`position: absolute` が付いている。ボタンは絶対位置でゼロ幅のコンテナに配置され、内容が圧縮されて86pxの高さに伸び、下部が直接画面に表示される。修正方法は明示的に `position: static` を使ってドキュメントフローを取り戻すことだ。

共有スタイルを再利用する前に、どのような隠蔽的な制約があるかを見てみよう。

## 品質は本当に良いか

正直に言うと、2つのレベルがある：

**記事内容：予想以上に良い。** Markdown構造、画像のパス、行内コードがすべて保持されており、文章も流れるように読める。韓国語の敬語体系も一致している。1.8Bの小さなモデルでは記事を書けないが、読むには十分だ。

**UIの短い文：人工の校正が必要。** 464件のうち約10%に致命的な問題があるが、それらは予想可能なカテゴリー（曜日、単位、時制、用語）に集中しているので、リストを参照して確認すれば問題ない。

- **Glossary**: 留仙洞 → Liuxiandong
- 鸣潮 → Wuthering Waves
- 博主/站名 Suni → Suni
- 汇文明朝体 → Huiwen Mingcho (font name)

人工校对的活被管线设计压到了最小：增量不覆盖、零格式 diff、校对的成果永远安全、重跑一万次也不会被冲掉。

## 现在加一门新语言要多久

架构全部参数化之后，只剩三步：

```ts
// 1. 注册语言码和显示名
const LOCALES = ['zh', 'en', 'ja', 'ko', 'fr']
```

```bash
# 2. 実行翻訳パイプライン、ローカルモデルを全自動で処理
TRANSLATE_TARGET=fr pnpm i18n:dict
TRANSLATE_TARGET=fr pnpm i18n:content
```

3. 日付のフォーマットを追加し、高リスク項目の人工校正を行う（曜日、単位、チュートリアルの枠組み）

機械時間は20分、人間時間は30分。今後新しい記事を書く際は翻訳を心配する必要はなく、`pnpm i18n:content --skip-existing` を使って不足している言語バージョンを増量翻訳するだけでよい。

## 結び

最初の要求は一言：「ブログが中国語のみで、良くない。」最終的に得られたのは持続可能な多言語システムです：翻訳のパイプライン、校正リスト、新言語の3ステップ入力、新記事の自動補完翻訳があります。

ちなみに、この記事の英語、日本語、韓国語の3つのバージョンも、このパイプラインで翻訳されています——記事自体が証拠です。言語を切り替えて体験してみてください。
