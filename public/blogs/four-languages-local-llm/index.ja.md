# Liuxiandongのブログ公開記：1.8Bのローカル小さなモデルを翻訳官に任せる

このブログは中国語のみで、良くない。

そのため、空いた時間を利用して、English、日本語、한국어を一気に学習した。全過程において、翻訳作業はほぼ地元の1.8Bバイトの翻訳小モデルに任され、私は校正とバグ修正のみを担当した。この記事は完全なレビューで、アーキテクチャの選択方法、翻訳パイプラインの構築方法、そして実際にリリースした時に直面するいくつかの問題点について説明している。

## 先に結論を言う

- 全站 UI 文案 464 条 × 3 语种，访客侧和管理侧全覆盖（写作后台、站点配置弹窗这些也算）
- 13 篇文章全文 × 3 语种 = 39 篇译文，外加关于页、友链、项目、图片、句子的数据变体
- 共 5 个提交、319 个文件变更
- 左下角语言菜单切换，选择持久化，`<html lang>` 跟着变

効果はどうか？言語を切り替えて実際に操作してみればわかる。

## なぜnext-intlを使わないのか

実際に使ってみる前にnext-intlのような成熟したソリューションを真剣に検討したが、最終的に断念した。その理由は、私たちのブログの構造が非常に特殊だからである：記事の本文はGitHubリポジトリに存在し（`public/blogs/<slug>/index.md`），実行時にfetchで取得してレンダリングするため、まるで「GitHubがデータベースである」ような状態になる。このようなクライアントレンダリング＋静的データファイルの構造では、localeルーチンを使うのは単なる手間になる。

最後に最も軽い方法を選択した：自作辞書 + React Context + localStorageの持久化処理を採用し、サイト内に既存のフォント切替え機構と完全に同構造である。核心は3つのファイルだけだ：

- `config.ts`：言語コードの登録表、表示名、`htmlLang`のマッピング
- `translate.ts`：二層の辞書値取得、keyが欠落時は自動的に中国語に戻る、決して画面が真っ白になることはない
- `locales.ts`：各言語辞書の登録入口

重要な選択の一つとして正直に言うと、英語モードではURLを変更せず、`/en/`のルートもないため、SEO面で不利になる。個人ブログではこの点は問題ないが、商業サイトとしてはよく考えてみてほしい。

コンテンツファイルについては「変体サフィックス」の規定に従う：`index.en.md`、`index.ja.json`、`list.ko.json`……実行時に現在の言語バージョンを優先的に読み込み、ファイルが存在しない場合は中国語の原文に戻る。したがって、いつでも一部の翻訳ファイルのみをアップロードしても、サイトは完全な状態を保つことができる。

## 翻訳官は誰ですか

地元でOpenAI対応の推論サービスを立ち上げ、2つのモデルを追加しました。

- 主力：**Hy-MT2-1.8B**，腾讯の混元翻訳専用モデル、4bit量化。翻訳専用の小さなモデルで、速くて安定している
- 備胎：Qwen3.8-27B、特定言語や単文が不満足な場合に使用する代替モデル

提示词の設計は没入型翻訳プラグインを参考にした。訳文のみを出力し、段落数は一致させる必要がある。複数段落は `%%` で区切る。最後の項目は重要だ——記事を空行で分割し、隣接する段落を一括として扱い（各一括に最大4段落）、一度に一括で翻訳し、`%%` で分割して適切に配置する。一括が多いほど段落の不整合が生じやすい。没入型翻訳がデフォルトで4段落を採用しているのは理にかなっている。実験で4段落を超えると段落が失われる。

管線スクリプトには合計6つのファイルがあり、2つの入力があります：

- `i18n:dict`：UI翻訳辞書（zh域ファイル → en/ja/ko域ファイル）
- `i18n:content`：内容の翻訳（記事のMarkdown、config、各種索引JSON）

囲いコードブロックは全てスキップし、frontmatterも翻訳しない。バッチ翻訳が失敗した場合は自動的に段落ごと翻訳に切り替わり、さらに段落が失敗した場合は中国語のまま保持される——構造は常に一致し、最悪の場合はその一節だけが翻訳されない。

また、デザインが後続の問題を救ってくれる：**インクリメントセマンティック、再実行でカバーしない**。辞書ファイルに既にある翻訳内容（中国語以外）はそのまま保持し、新規追加されたkeyのみを翻訳する。内容ファイルには `--skip-existing`を付けておくことで、既にある翻訳は直接スキップされる。このように「一つの文案を変更 → 一度実行 → 一節を校正」というサイクルが成立すれば、そうでなければ毎回の再実行で手作業の校正が消えてしまい、誰も救えない。

工程詳細として、生成器が出力する文字列の字面量は倉庫の prettierスタイルに合わせられている（デフォルトでは単一の引用符が使用され、内容に引用符が含まれる場合のみ二重引用符で囲まれる）。gitではフォーマットのノイズが発生しない。

## 多主体分業

文案抽出のような作業は量が多いがパターンが固定されているため、多主体の並行処理に最適である。訪問者側には4つのagentが配置され、各々が特定の分野を改造する（ブログ、音楽、コンテンツ集合、ツールボックス）。管理側にも4つが配置され（書き込みバックエンド、設定ダイアログ、管理ツールバー、ダイアログとtoast）、最後に2つは監査agentで、1つはデータの完全性をチェックし、もう1つはlocaleの知覚漏れをチェックする。

開始前に規範を定めておく：辞書は業務領域ごとにファイルを分割し、keyの命名規則、enディレクトリの変更を禁止（翻訳ラインに任せる）、参考実装を先に行う（私が4つのファイルを先に修正してサンプルとする）。このようにしてagent間の衝突が起きず、出力物は直接使用可能になる。

## リオシアンドンに触れた後に見つけた問題点

### 1. 月曜日が「One」と翻訳されている

中国の曜日リスト `['一','二','三',...]` をモデルに渡し、英語版が戻ってきた内容は：

> One / Two / Three / 4 / 5 / 6 / Day

最初の3つは大文字の数字として理解され、中間の3つはアラビア数字を正直に翻訳しており、最後の「日」は正しく翻訳されている。日本語版はさらに驚異で、一、二、三は元のまま保持されている——日本語では実際に数字として使えるからだ。

修正方法は非常に簡単：手作業で書き直す。Mon/Tue/Wed、月火水木金土日、월화수목금토일。教訓は**文脈から離れた短いタグは翻訳器の天敵である**：曜日、単位（「時/分/秒」が Hour/Minuteの単数形に翻訳される）、ボタン（「转换」が进行时 Convertingに翻訳される）、この種類は手作業で対処する必要がある。

### 2. 文の中に埋め込まれた断片は翻訳できない。

Wuthering Wavesのカード分析ページには使用マニュアルがある。「F12をクリックし、右側の Networkパネルをクリック」——F12とNetworkはJSX内で強調された`<span>`であり、全文が辞書内の前後断片に分かれている。モデルをこの種の断片で翻訳する際は前後文が全くなく、韓語ではさらに困難である：助詞が前の単語に付着し、分割された骨格は元に戻すことができない。

単語ごとに対応するのを諦め、スロットの位置に基づいて全体の文構造を再構築する方法で、3つの言語それぞれに自分の語順に合ったバージョンを1つずつ書く。これが国際化コンテンツデザインの最初のレッスンです：**完全な文を翻訳器に任せて、断片を与えないこと**

### 3. 用語の逸脱

13つの記事のタグはそれぞれ独立して翻訳されており、同じ「Liuxiandong」は2つのバージョンが出ています。「pretext」は「背景」と訳され、インターネット上の「代理」は「代理商」と翻訳され、韓語版「명조」の公式名は文字が間違っています。最後にスクリプトを使って中国語の原文と照合し、3つの言語の用語表を一致させます。

正しいやり方は、翻訳前に用語表を提供するか、翻訳後に一通りの一致チェックを行うことです。固有名詞については、モデルが自動的に統一されることを期待してはいけません。

### 4. `useState(props)`：カードは言語切替えと連携しない

最も隠蔽的なものです。Suniのカードコンポーネントにはこの行があります：

```ts
const [localBlogger, setLocalBlogger] = useState(blogger)
```

stateはプロパーを初期化時に一度コピーされるだけです。言語を切り替えた後、リストデータは変わりますが、keyは変わらず、コンポーネントも再インスタンス化されません。カード内部には最初にページに入った時の言語が保持されます。当時の現象は非常に奇妙でした：React fiber内ではプロパーが日本語であり、画面にはまだ中国語が表示され、consoleには何も記録されませんでした。

修法一行：リストに `key={locale}` を追加して強制的に再構築する。教訓：**「props から初期化される state」は自然と prop の変化に反応しない**、言語やテーマなどのグローバルなコンテキストが最も問題になる。

### 5. 多言語は単なる翻訳ではなく、データの一貫性である

3つの連鎖的な問題がすべて「書き出し」の側にある：

- 編集保存のプロセスが「現在の言語のマージビュー」を使っている場合、日本語モードで一度保存すると、日本語のタイトルが中文の `index.json` に書き込まれる——データソースが翻訳結果によって汚染される
- 記事の削除では中文のインデックスのみが削除され、英日韓のインデックスには孤立した記事が残り、それらの言語に切り替えて開くと 404エラーが発生する。これがユーザーが報告する「フロントエンドで時々エラーが発生する」の真の原因である
- 日本語では7つの記事が「要約」として分類されているが、分類リストでは「まとめ」と呼ばれている。同じ意味を持つが2つの異なる翻訳名があり、グループ分けが正確に合わない

**「表示」の解決はできても「書き込み」の解決はできない。データソースに書き込むすべてのリンクは、元言語に固定されなければならない。**

### ハッピーエンド：言語ボタンが画面外に飛び出す

新しく作った左下角の言語ボタンは `card.base` のスタイルを使用している——これはホームページでの自由なドラッグカード用であり、自動的に `position: absolute` が設定されている。ボタンは絶対位置でゼロ幅のコンテナに配置され、内容が圧縮されて86pxの高さに伸び、下部が直接画面に表示される。解決方法は明示的に `position: static` を使用してドキュメントの流れを取り戻すことだ。

共有スタイルを再利用する前に、どのような隠れた制限があるかを見てみよう。

## 品質は本当に良いか？

正直に言うと、2つのレベルがあります：

**文章正文：予期せぬほど良いです。** Markdown構造、画像パス、行内コードをすべて保持し、文章が流れるように、韓国語の敬語体も一致しています。1.8Bの小さなモデルでは文章を書けませんが、文章を読むには十分です。

UIの短文：人手による校正の必要性。464件のうち約一割に不備があったが、いずれも予想できるカテゴリ（曜日、単位、時制、用語）に集中していたので、チェックリストに沿って一つずつ確認すればよい。

人工校对的作業がパイプライン設計によって最小限に抑えられている：增量がカバーされず、ゼロフォーマットのdiffが適用され、校正された成果は常に安全であり、1万回再実行しても破損しない。

## 現在、新しい言語を追加するのにどれくらい時間がかかるか

アーキテクチャの全てのパラメータ化が完了した後、残るのは3ステップだけ

```ts
// 1. 言語コードと表示名の登録
const LOCALES = ['zh', 'en', 'ja', 'ko', 'fr']
```

```bash
# 2. 翻訳ラインを実行し、ローカルモデルを全自動で処理
TRANSLATE_TARGET=fr pnpm i18n:dict
TRANSLATE_TARGET=fr pnpm i18n:content
```

3. 日付のフォーマットを追加し、高リスク項目の人工校正を行う（曜日、単位、チュートリアルの骨格）

機械時間は20分、人工時間は30分。今後新しい記事を書く際は翻訳を心配する必要はなく、`pnpm i18n:content --skip-existing` を使って不足している言語バージョンを增量的に翻訳するだけでよい。

## 末尾

最初の要求は一言：「ブログが中国語のみで、良くない。」最終的に得られたのは持続可能な多言語システムである：翻訳のパイプライン、校正リスト、新言語への3ステップアクセス、新記事の自動補完翻訳。

ちなみに、この記事の英語、日本語、韓語の3つのバージョンも、このパイプラインで翻訳されている——記事自体が証拠である。言語を切り替えて体験してみてほしい。
