# 四语博客上线记：让本地 1.8B 小模型当翻译官

这个博客只有中文，不好。

于是趁着有空，一口气把 English、日本語、한국어 全上了。整个过程中，翻译工作基本都交给了本地一个 1.8B 的翻译小模型，我只负责校对和修 bug。这篇文章是完整复盘：架构怎么选、翻译管线怎么搭、以及几个只有真正上线才会踩到的坑。

## 先说结论

- 全站 UI 文案 464 条 × 3 语种，访客侧和管理侧全覆盖（写作后台、站点配置弹窗这些也算）
- 13 篇文章全文 × 3 语种 = 39 篇译文，外加关于页、友链、项目、图片、句子的数据变体
- 共 5 个提交、319 个文件变更
- 左下角语言菜单切换，选择持久化，`<html lang>` 跟着变

效果如何，你切个语言到处点点就知道了。

## 为什么不用 next-intl

动手前认真考虑过 next-intl 这类成熟方案，最后放弃了，原因是我们博客的形态太特殊：文章正文存在 GitHub 仓库里（`public/blogs/<slug>/index.md`），运行时 fetch 回来渲染，等于「GitHub 就是数据库」。这种客户端渲染 + 静态数据文件的架构，上 locale 路由纯属给自己找事。

最后选了最轻的方案：自建字典 + React Context + localStorage 持久化，和站内已有的字体切换机制完全同构。核心只有三个文件：

- `config.ts`：语言码注册表、显示名、`htmlLang` 映射
- `translate.ts`：两级字典取值，缺 key 自动回落中文，永不白屏
- `locales.ts`：各语言字典的注册入口

一个关键取舍要诚实说：英文模式不改 URL，没有 `/en/` 路由，SEO 上吃亏。个人博客我对这点无所谓，做商业站请三思。

内容文件则走「变体后缀」约定：`index.en.md`、`index.ja.json`、`list.ko.json`……运行时优先加载当前语言版本，文件不存在就回落中文原文。所以任何时刻只上传了一部分译文，站点也是完整的。

## 翻译官是谁

本地起了一个 OpenAI 兼容的推理服务，挂了两个模型：

- 主力：**Hy-MT2-1.8B**，腾讯的混元翻译专用模型，4bit 量化。翻译专用小模型干翻译，又快又稳
- 备胎：Qwen3.8-27B，个别语种或单篇不满意时换它重跑

提示词的设计参考了沉浸式翻译插件：只输出译文、段落数必须一致、多段用 `%%` 分隔。最后这条是灵魂——把文章按空行切段，相邻段落凑批（每批最多 4 段），一次请求翻一批，回来按 `%%` 拆开对号入座。批越大越容易缺段错位，沉浸式翻译默认 4 段是有道理的，我实测超了就开始丢段落。

管线脚本一共六个文件，两个入口：

- `i18n:dict`：翻 UI 字典（zh 域文件 → en/ja/ko 域文件）
- `i18n:content`：翻内容（文章 markdown、config、各种索引 JSON）

围栏代码块整个跳过不翻，frontmatter 不翻，批翻译失败自动降级成逐段翻，单段再失败就保留中文——结构永远对齐，最坏情况只是那句没翻。

还有一个设计救了后面所有事：**增量语义，重跑不覆盖**。字典文件里已有的译文（非中文内容）原样保留，只翻新增的 key；内容文件带 `--skip-existing`，已存在的译文直接跳过。这样「改一条文案 → 跑一次 → 校对一条」的循环才成立，不然每次重跑都把人工校对冲掉，谁也救不了。

顺带一个工程细节：生成器输出的字符串字面量对齐了仓库 prettier 风格（默认单引号，内容含单引号才换双引号包裹），重跑零 diff，git 里不会出现格式噪音。

## 多智能体分工

文案抽取这种活，量大但模式固定，最适合多智能体并行。访客侧派了 4 个 agent 分域改造（博客、音乐、内容集合、工具箱），管理侧又 4 个（写作后台、配置弹窗、管理工具条、对话框与 toast），最后 2 个审计 agent，一个查数据完整性、一个查 locale 感知遗漏。

开工前把规范钉死：字典按业务域拆文件、key 命名规则、en 目录禁改（留给翻译管线）、参考实现先行（我自己先手改 4 个文件当样板）。这样 agent 之间不会互相冲突，产出直接可用。

## 上线后才踩到的坑

### 1. 星期一被翻成 "One"

把中文星期数组 `['一','二','三',...]` 丢给模型，英文版回来的是：

> One / Two / Three / 4 / 5 / 6 / Day

前三个被理解成数字大写，中间三个很诚实地翻了阿拉伯数字，最后一个「日」倒是翻对了。日文版更绝，一二三原样保留——毕竟日语里它们真的能当数字用。

修法很简单：人工重写。Mon/Tue/Wed、月火水木金土日、월화수목금토일。教训是**脱离上下文的短标签是翻译器的天敌**：星期、单位（「时/分/秒」被翻成 Hour/Minute 单数）、按钮（「转换」被翻成进行时 Converting），这一类都得人工过。

### 2. 嵌在句子里的碎片翻不了

鸣潮抽卡分析页有个使用教程，「点击 F12，点击右侧 Network 面板」——F12 和 Network 是 JSX 里高亮的 `<span>`，整句被拆成前后片段存在字典里。模型翻这种碎片时完全没有前后文，韩语更是灾难：助词粘在前一个词上，拆开的骨架根本拼不回去。

修法是放弃逐词对应，按槽位重写整句骨架，三种语言各写一份符合自己语序的版本。这是国际化文案设计的第一课：**把完整句子交给翻译器，别给它碎片。**

### 3. 术语漂移

13 篇文章的 tags 是逐篇独立翻译的，同一个「留仙洞」翻出了两个版本，「pretext」被意译成「背景」，网络「代理」被翻成「代理商」，韩语版「鸣潮」的官方名（명조）还错了字。最后写脚本对照中文原文逐条修正，把三种语言的术语表对齐。

正确姿势是翻译前就给术语表（glossary），或者翻完跑一遍一致性对齐。专有名词永远不要指望模型自己统一。

### 4. `useState(props)`：卡片不跟语言切换

最隐蔽的一个。博主卡片组件里有这么一行：

```ts
const [localBlogger, setLocalBlogger] = useState(blogger)
```

state 只在挂载时拷贝一次 prop。切语言后列表数据换了，但 key 没变、组件不重挂，卡片内部还是第一次进页面时的语言。当时的现象非常灵异：React fiber 里 props 已经是日文，屏幕上还是中文，console 干干净净。

修法一行：列表加 `key={locale}` 强制重建。教训：**「从 props 初始化的 state」天然不响应 prop 变化**，语言、主题这类全局上下文最容易踩中它。

### 5. 多语言不只是翻译，是数据一致性

三个连环坑，全都出在「写入」侧：

- 编辑保存链路如果拿的是「当前语言的合并视图」，日语模式下保存一次，日文标题就写进中文 `index.json`——数据源被译文污染
- 删除文章只删了中文索引，英日韩索引里残留孤儿条目，切到那些语言点开就 404，这就是用户报的「前端有时报错」的真凶
- 日语里 7 篇文章的分类是「要約」，分类列表里却叫「まとめ」，同一含义两种译名，分组直接对不上

**翻译解决「显示」，解决不了「写入」。凡是往数据源写的链路，都必须钉死在源语言上。**

### 彩蛋：语言按钮飞出屏幕

新做的左下角语言按钮复用了 `card.base` 样式——那是给首页自由拖拽卡片用的，自带 `position: absolute`。按钮被绝对定位进一个零宽容器，内容压缩换行撑到 86px 高，下半截直接出屏。修法是显式 `position: static` 夺回文档流。

复用共享样式前，先看它带了哪些隐藏约束。

## 质量到底行不行

说实话分两档：

**文章正文：出乎意料地好。** markdown 结构、图片路径、行内代码全部保留，语句通顺，韩语连敬语体都保持一致。1.8B 的小模型写不了文章，但翻文章绰绰有余。

**UI 短句：需要人工校对。** 464 条里大约一成有硬伤，但都集中在可预期的类别里（星期、单位、时态、术语），照着清单过一遍就行。

人工校对的活被管线设计压到了最小：增量不覆盖、零格式 diff，校对过的成果永远安全，重跑一万次也不会被冲掉。

## 现在加一门新语言要多久

架构全部参数化之后，只剩三步：

```ts
// 1. 注册语言码和显示名
const LOCALES = ['zh', 'en', 'ja', 'ko', 'fr']
```

```bash
# 2. 跑翻译管线，本地模型全自动
TRANSLATE_TARGET=fr pnpm i18n:dict
TRANSLATE_TARGET=fr pnpm i18n:content
```

3. 补一条日期格式，人工校对高危项（星期、单位、教程骨架）

机器时间二十分钟，人工半小时。以后写新文章也不用惦记翻译，`pnpm i18n:content --skip-existing` 增量补翻缺的语言版本就行。

## 尾巴

最开始的需求一句话：「博客只有中文，不好。」最后收获的是一套可持续的多语言系统：翻译有管线、校对有清单、新语言三步接入、新文章自动补翻。

对了，本篇文章的 English、日本語、한국어 三个版本，也是这套管线翻的——文章自己就是证据。切个语言感受一下吧。
