# 人需要 Idle：写在离职之前

![刚入职不久时拍下的深圳晚霞](/images/pictures/41c9e9b45e09d1fbf8c62050b5638051bccf9e93b3a5a55eefc9d0e862bf3347.webp)

这张照片拍在五月十四日，刚入职不久。那天看到晚霞落在深圳的楼群上，天空是很浓的橘红色，我忽然对这座城市和接下来的生活有了很多期待。

那时候，我觉得这会是一份非常好的工作。项目有意思，AI 每天都在变化，许多东西还没有固定答案，正好可以凭着一点少年稚气和自由意志往前闯。

现在回头看，我也不觉得当时看错了。这份工作依然有它好的地方，我也确实在这里做成了许多以前没有做过的事。只是照片里的那股劲，到了今天，好像低迷了一些。

最近我在写离职交接。

一开始整理出一千多行，我看完只有一个感觉：不够。这是我连续做了五个月的项目，怎么可能一千多行就讲完？于是继续往里补，把接口、页面、状态、部署、配置和踩过的坑一件件写下来。最后，那份 Markdown 长到了四千六百多行。

写到这个长度，我才第一次从工作里退后一点，看清这几个月到底发生了什么。

从四月到现在，我做的是一个 AI 数学教育视频项目。说是开发，其实什么都做过：前端、后端、模型调用、Agent、任务队列、语音、渲染、部署、监控，还有线上出问题以后，把散落在数据库、日志和服务器里的线索重新拼起来。

我也在这五个月里，慢慢改变了自己对 AI、Agent 和工作的理解。

## 四月，先让它跑起来

四月时，事情推进得很快。

模型生成的代码会被截断，就做续写；公式渲染会出错，就补预处理；视频时长不准，就加规划；任务看起来在排队，最后发现可能只是数据库连接已经断了。语音、图片、支付、权限、管理后台和部署，也都在同一段时间往前赶。

那时我对 AI 最直接的感受就是：快。

它能读很多代码，能同时理解前后端，也能把一个模糊需求迅速变成可以运行的东西。以前可能要排好几天的修改，现在一天里就能来回做很多轮。问题出现以后，我也习惯继续把日志和代码交给 Codex，让它查，让它改，再让它验证。

这种速度很容易让人兴奋。好像只要模型再强一点、上下文再长一点、提示词再完整一点，许多工程问题就会自然消失。

后来我才发现，AI 确实把开发速度拉高了，但它也会把混乱一起加速。

一个边界不清楚的需求，可以更快地变成代码；一个没有事实源的判断，可以更快地扩散到整条链路；一个本来只该修局部的问题，也可能被它热心地重写一遍。速度本身不会替人决定什么该做，也不会替系统承担最后的结果。

## 有 Agent，不等于它真的会做事

六月时，我问过一个很直接的问题：我们的 LangGraph 还有用吗？为什么感觉不到很强的 Agent 效果？

查完以后，答案有点尴尬。它确实在线，节点在运行，事件也在产生。从程序结构上说，当然可以叫 Agent。但用户真正看到的，仍然更像一条带着模型的工作流：生成、检查、修复、再试一次，直到预算耗完或侥幸通过。

更让我在意的是，同一个失败任务，Codex 手动排查时可以修好，系统里的 Agent 却经常在原地转圈。

差别不只是模型。

手动修复时，我会先确认失败发生在哪里：数据库里是什么状态，事件走到了哪一步，生成代码是不是完整，渲染日志报了什么，最终视频到底有没有产出。找到真正的断点以后，只改最小的一块，再独立验证一次。

而当时的 Agent 有很多检查器、修复器和重试预算，却缺少这样一条统一的判断路径。它会做动作，但不一定知道哪个动作最值得做；会收到错误，却不一定能分清是代码问题、工具问题、模型问题，还是任务早就完成了，只是状态没有正确写回。

这件事改变了我对 Agent 的理解。

Agent 不是把大模型塞进一个循环里，再给它几个工具。真正有用的 Agent，需要知道事实在哪里，能看见自己刚刚做了什么，失败后拿到准确反馈，也要知道什么时候应该停下来，把问题交给确定性的规则或者人。

所谓自主，不是一直行动。能够克制，也是一种能力。

## 从“让 AI 写”到“让 AI 对结果负责”

到了七月和八月，我的大部分工作已经不再是单纯让 AI 生成代码。

我们试过让 Agent 原生读取和编辑文件，让两个 Reviewer 分别检查，再由 Coder 修改，最后重新渲染和检测；也把几何、函数、计算题里的经验拆成二十五份很小的 Prompt Skills，需要时再组合进去。

这些实验让我越来越确定：上下文不是越多越好，规则也不是越长越好。

把所有经验塞进一个巨大提示词，模型很容易顾此失彼。更有效的办法，是把任务拆成边界清楚的小能力：什么时候读取，允许改哪里，用什么事实判断，修改后必须重新检查什么。每一块都很小，却能被组合、替换和复用。

这和写普通软件其实没有本质区别。我们还是要定义接口、状态和责任，只是其中一部分执行者变成了 AI。

我也不再轻易相信“成功”两个字。

接口返回 200，不代表功能真的可用；服务显示 active，不代表正在跑的是新代码；队列确认了消息，不代表任务已经交付；数据库写着 SUCCESS，不代表视频能够播放；服务器上有一个 MP4，也不代表用户拿到的是这一版。

对这个项目来说，真正的完成要一路确认到最终产物：代码版本、运行进程、任务状态、文件身份、视频信息、Range 请求，最后还要真的点开播放。

AI 越能干，人越需要把“完成”定义得具体。否则它只会非常勤奋地完成一个错误目标。

## 后来，我成了那条主线程

项目逐渐稳定，普通题目开始可以批量生产，也走到了准备交付和继续扩大的阶段。照理说，我应该比刚开始轻松一点。

但我的感受正好相反。

解题链路要维护，前端要改，服务器要看，客户反馈要跟，临时需求会插进来，任何一个环节出问题，最后似乎都会回到我这里。我经常觉得自己像一条 Node.js 的主线程，不断接收 Event，不断发生 Context Switch。

系统里的队列拥堵了，我们会看并发、背压和超时；机器没有余量了，我们会加容量、做限流、安排重试。但轮到人的时候，好像只要还能回应，就默认可以继续塞任务。

可人需要 Idle。

Idle 不是偷懒。没有空闲，脑子就来不及整理刚刚发生的事情，也无法进入一段完整的思考。很多真正重要的判断，并不是在消息不断弹出来时做出的。它需要一两个小时不被打断，有时甚至需要下班以后彻底不想工作。

七月生日那天，我忙到晚上十一点四十分，母亲问我今天去哪里玩，我才想起原来那天是自己的生日。后来在留仙洞散步，抬头看到写字楼一格一格亮着，第一次很具体地看见深圳的“班味”。

这些事情当时都被我写进了博客。现在回头看，它们其实早就在提醒我：工作已经不只是占用了时间，它开始拿走我感受时间的能力。

## 我为什么决定离开

我要离开的，并不是这个项目本身。

我仍然喜欢把 AI 能力变成真正能运行、能交付的系统。比起做一个演示，我更在意任务如何恢复，状态由谁负责，异常发生以后怎样留下证据，最后的东西能不能真的到用户手里。这些依然是我想继续做的工作。

我想离开的是另一件事：长期由一个人充当整个项目的调度器。

我希望下一份工作里，职责可以更清楚一些。让我专心维护好一条核心链路，有统一的需求入口，有人安排优先级，也有人承接其他方向。工作当然还是会有压力，也不可能因为换了一个单位就自动变轻松，但至少我想确认，自己面对的是一个团队，而不是另一个换了名字的单线程循环。

离开也不完全是一种否定。

五个月里，这个项目从不断试错，走到了能够生产、评审和交付的阶段。我开始整理新人要接手的岗位，写下那份四千六百多行的交接文档，把以前只有我知道的事情尽量变成别人也能找到的路径。

能交出去，本身也是项目成熟的一部分。

## 写在还没有离开的这几天

我现在还没有完全离开。电脑里还有要核对的文档，服务器上还有要确认的版本，也还有一些问题，我知道它们不会因为我提交离职就马上消失。

只是心态已经有了一点变化。

以前我总想着，再把这个问题修完，再把那条链路补上，项目就会进入一个终于轻松的状态。现在我知道，系统永远会有下一个事件。真正的边界不能等事件自己消失，只能由人做出选择。

这五个月，我学会了怎样让 AI 写生产代码，怎样让 Agent 使用工具，怎样用证据确认一个任务真的完成。

临近离职，我还想学会一件更普通的事：不把自己也当成一个必须永远在线的服务。

系统可以持续运行。

人应该偶尔空闲。

也希望下一次再遇见这样的晚霞时，我还有心情停下来拍一张。不是因为下一份工作一定更好，只是希望那股有点稚气的自由意志，能慢慢回来。

爱你老己。
