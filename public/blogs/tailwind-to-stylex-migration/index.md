先从结论说起：这次我把整个博客的样式体系从 Tailwind 换成了 StyleX。21 条路由、133 个文件的改动、19 次提交。主样式表从 97.7 KB 瘦到 60.3 KB（-38%），构建和运行时……基本没变。

**整个博客长这样——和迁移前一模一样。**

一模一样，就是这次迁移最大的成功。

## 为什么要拆掉好好的 Tailwind？

先自证清白：Tailwind 没惹我。它很好用，类名字符串往 JSX 上一贴，半小时能糊出一个页面，我这博客就是它喂大的。

但我对 StyleX 馋了很久——它不是野路子，是 Meta 出品：2020 年在 Facebook 内部孵化，2023 年底开源，Instagram、WhatsApp 生产环境跑了五年。它和 Tailwind 是两种哲学：

- **Tailwind 是字符串艺术**：`className="flex gap-2 px-4"`，所见即所得，但拼错了没人告诉你——样式只是「悄悄不生效」
- **StyleX 是 TypeScript 对象**：`stylex.create({ ... })`，写错属性名、放错值，`tsc` 当场把错误糊你脸上

最打动我的三点：

1. **类型安全**：样式第一次进了类型系统，拼写错误从「没反应」升级成「编译报错」
2. **确定性**：Tailwind 靠扫描器猜「哪些类被用了」——这有一堆玄学（模板字符串拼出来的类名扫不到、注释里写个类名反而会被打进产物）；StyleX 靠编译器知道「哪些样式被引用了」，没有猜测，就没有玄学
3. **体重**：只产出被真实引用的原子类，一个值全站复用一个类

当然，还有个更朴素的原因：博客是我的实验田。不拿它下地，难道拿公司项目吗？

顺便说破 StyleX 的原理，它其实很朴素：你写 TS 对象，编译期把它拆成**最细粒度的 CSS 原子类**（一个类只管一个属性），运行时就是个查表。**没有运行时样式注入**——CSS 在构建时就生成好了，不占 JS 一分钱。零运行时、原子类、类型安全，这三点凑齐了。

## 策略：先同居，再分手

一百多个文件不可能一夜换掉，我用的是「双管线」策略。

**第一阶段：两个框架和平共处。** Tailwind 和 StyleX 同时装，靠 CSS 的 `@layer` 排座次：

```css
@layer theme, base, components, priority1, ..., priority9, utilities;
```

StyleX 的原子类夹在中间（priority1-9 是它的地盘），老组件继续吃 Tailwind，新组件上 StyleX，各论各的。

**第二阶段：按目录分批搬家。** 133 个文件拆成 7 个波次，一波一个目录，每波搬完当场验收：类型检查 + 生产构建 + 浏览器逐页实测。

**第三阶段：分手。** 全部搬完后的某天凌晨，删掉 Tailwind 的 5 个依赖、清掉所有自定义工具类，收工。然后就是下面这五个坑的故事。

## 踩坑记录（精选五个）

### 坑一：`@stylex;` 指令被 Tailwind 整个吞了

StyleX 的构建需要一个魔法指令：在 CSS 里写一行 `@stylex;`。

诡异的事情来了：配置全对、构建全绿，但产物里**一个原子类都没有**。排查了 90 分钟，最后把 CSS 入口的编译过程 dump 出来逐层对比，才找到真相：

Turbopack 对每个 CSS 入口**逐个**跑 PostCSS 插件链，而 Tailwind 处理文件时会把整个文件「重新编译一遍」，过程中底层编译器把不认识的 `@stylex;` 当垃圾清掉了。指令无论写在自己文件里还是被 import 进来，都逃不过。

**解法**：把 `@stylex;` 放进一个独立的小 CSS 入口，这个文件全程不碰 Tailwind，指令就能活到该读它的插件手上。

### 坑二：两个来源的 stylex 类名，千万别用 cn() 拼

这条是实验加构建产物双重实锤的：

StyleX 的合并语义很清晰——**同一次 `stylex.props()` 里，后写的覆盖先写的**，被覆盖的原子类会直接从输出里移除。

但是！如果你把两个来源的 stylex 类名用 `cn()` 字符串拼在一起，冲突就变成按「字典序排版」解决——`padding: 12px` 会输给 `padding: 24px`，你写的顺序完全不算数。

**铁律**：覆盖语义必须走同一次 `stylex.props()`，`cn()` 只配用来透传外来类。

### 坑三：group-hover 怎么办？marker 来救

Tailwind 有个神器 `group-hover:`——父元素悬停，子元素联动。StyleX 没有祖先选择器，这东西怎么迁？

答案是 StyleX 的 marker 机制：

```ts
// 1. 定义一个标记
export const hoverGroup = stylex.defineMarker()

// 2. 容器带上标记（替代原来的 'group' 类）
<div {...stylex.props(styles.wrap, hoverGroup)}>

// 3. 子元素用条件样式
const styles = stylex.create({
  overlay: {
    opacity: {
      default: 0,
      [stylex.when.ancestor(':hover', hoverGroup)]: 1,
    },
  },
})
```

编译出来的核心规则大概长这样：

```css
/* 悬停「最近的带标记祖先」时，遮罩显现 */
.overlay:where(.marker:hover *) { opacity: 1; }
```

**语义和 Tailwind 的 group-hover 完全一致**——只认最近的标记祖先，列表里悬停一张卡片不会误伤同层其他卡片。

还有个意外收获：逐处对照原项目审计时发现，**好几处 group-hover 本来就是死代码**（写样式的子元素压根不在 group 容器里，从上线第一天起就没生效过）。迁移顺手做了次「悬停效果尸检」，死的就埋了，按原样保真。

### 坑四：拆 Tailwind 那天，地基也跟着走了

这是最惊险的一个。

Tailwind 除了满屏的工具类，还悄悄给全站垫了一层 **preflight**（基础重置）：`box-sizing: border-box`、链接颜色继承、表单字体继承、图片 `display: block`……全是那种「你感觉不到它、但抽掉就出事」的东西。

拆除当晚一切正常。第二天巡检时才发现：博客列表的标题变成了**浏览器默认的蓝色下划线链接**——回头一查，全站的 `box-sizing` 也悄悄变回了 `content-box`。

这种回归肉眼看截图根本发现不了（大部分组件样式都是显式的），是拿新旧两版**逐元素对比计算样式**才揪出来的。修复方式：把 Tailwind v4 的 preflight 源码逐行移植回来，只替换掉其中的 Tailwind 私有函数。

教训：**拆任何东西之前先问——它除了表面的功能，还给你垫了什么？**

### 坑五：一明一暗，两种幽灵类名

- **明的**：Tailwind 的扫描器会把**注释里**的类名当真，凭空产出 CSS。迁移后这个类别被根治——StyleX 不读注释。
- **暗的**：有个特效组件的文字层是运行时 `document.createElement` 动态赋类名的（不在 JSX 里），所有静态扫描都看不见它。Tailwind 拆掉后这两个类名变成「无定义悬空」，最后用「运行时类名赋值」模式全库扫描才扫出来，改了。

一个明着虚报、一个暗着漏报——扫描器式方案的两个经典软肋，这次齐了。

## 成绩单（诚实版）

| 指标 | 迁移前 | 迁移后 | 变化 |
|---|---|---|---|
| 主 CSS（raw） | 97.7 KB | 60.3 KB | **-38.3%** |
| 传输量（gzip / brotli） | 17.8 / 14.5 KB | 14.9 / 12.9 KB | -16% / -11% |
| 首屏 JS | 1246 KB | 1256 KB | +0.8%（基本没变） |
| 构建耗时 | ~4s | ~4s | 没变 |
| 运行时指标 | — | — | 没变 |

等等，为什么 raw 降了 38%，传输量只降了 10~16%？

因为**压缩器和原子去重是「替代关系」，不是叠加关系**：

- Tailwind 的产物重复度极高，gzip/brotli 能吃掉大部分冗余（压缩率 6.8 倍）
- StyleX 的原子表在编译期已经去过重了，剩下内容「熵」更高，压缩器没什么可吃（4.7 倍）

所以：raw -38% 是「样式引擎提效」的诚实数字，传输 -10~16% 才是「用户真实省下的流量」。两个口径必须分开说——**迁移不是跑分比赛，别拿 raw 数字吹传输。**

真正的收益藏在看不见的地方：弱网 + 低端机上，少 37 KB CSS 大约省几十毫秒的解析和内存；以及——**确定性**。

## 幕后：这活儿是「多智能体」干的

这次迁移有个好玩的执行方式：我没有一行行手写 133 个文件，而是当了回「总指挥」。

- 迁移拆成工单：按目录分波次，每波派给并行的「迁移员」智能体，规则写死在工单里（对照编译产物取精确值、注释不许写 Tailwind 类名防止扫描器提取、禁止自己跑构建……）
- 每一波交付后我验收：`tsc` + 生产构建 + 浏览器逐页实测
- 还设了「审计员」角色：专门去原项目翻旧账，抓出「原版就死掉的代码」，避免把 bug 一起当遗产搬过来

最魔幻的是收尾的仓库切换。我还在脑补「本地合并、推送、CI」的经典流程，它直接来了手**云端换血**：把新的提交历史强制推送成远端 `main`，再把本地仓库 `fetch + reset` 过来。我打开 Git Graph 一看——诶？怎么还是旧历史？差点以为被耍了。`git fetch` 一下，世界安静了：

- `main` = 全新 StyleX 版（19 次提交）
- `archive/tailwind-v4` = 旧版全部历史，同一个仓库里躺着当保险
- 后悔药：一条命令回滚

## 值不值得？

给想抄作业的人一个诚实清单：

**值得，如果你**：样式体积敏感、项目要长期维护、TypeScript 重度使用者、而且有闲心（最重要的一个）。

**缓一缓，如果你**：重度依赖 Tailwind 生态组件库（shadcn 之类拿来就用的）、项目临近交付、或者只是想做个小站。

对我来说值了——不只是省下的 38%，而是以后再也不会遇到「样式拼错不报错」「注释里的类名被扫进产物」「这坨 CSS 到底还有没有人在用」这类幽灵问题。样式终于变成了**有类型、有归属、可删除**的一等公民。

> 97.7 KB → 60.3 KB。
> 133 个文件，19 次提交，0 个用户能看出来的变化。
> 这可能就是重构最好的样子。
