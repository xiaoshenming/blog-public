まず結論から言うと、今回私はブログ全体のスタイルシステムを Tailwindから StyleXに変更した。21のルート、133のファイルの変更、19回のコミットがあった。メインスタイルシートは97.7 KBから60.3 KB（-38%）に減少したが、構築時と実行時の状態はほとんど変わっていない。

**ブログ全体の様子——移行前と全く同じです。**

全く同じであることが、今回の移行の最大の成功点だ。

## なぜ有効だった Tailwindを取り除くのか？

先自证清白：Tailwind は私に害を及ぼさなかった。非常に便利で、クラス名と文字列を JSX に貼り付けるだけで30分でページが作成できる。私のブログはまさにこれによって育てられたものだ。

しかし、StyleXに夢中になっている。これは無秩序なものではなく、Meta製品だ。2020年にFacebook内部で開発され、2023年末にオープンソースになり、InstagramやWhatsAppの生産環境で5年間使用されている。これはTailwindとは異なる哲学だ。

- **Tailwindは文字列の芸術**：`className="flex gap-2 px-4"`，見えるもの全てが使えるが、間違いを犯しても教えてくれない——スタイルはただ「静かに効果を発揮しない」だけだ。
- **StyleXはTypeScriptのオブジェクト**：`stylex.create({ ... })`，属性名や値を間違えても`tsc`が即座にエラーを表示してくれる。

私を最も感動させた3点：

1. **型安全性**：スタイルが初めて型システムに組み込まれ、綴りの間違いが「反応なし」から「コンパイルエラー」に変わった  
2. **確実性**：Tailwindはスキャナーで「どのクラスが使用されているか」を推測する——これには多くの謎が含まれる（テンプレストリングで作られたクラス名はスキャルできない、注釈にクラス名を書くと逆にプロダクトに含まれる）；StyleXはコンパイラが「どのスタイルが参照されているか」を知るため、推測がないので謎が生じない  
3. **重量**：実際に参照される原子クラスのみを生成し、一つの値で全サイトで一つのクラスを使用する

もちろん、もっとシンプルな理由もある：ブログは私の実験場だ。それを畑に使わないのなら、会社のプロジェクトを使うのか？

ついでStyleXの仕組みを話すと、実は非常にシンプルだ：TSオブジェクトを書くと、コンパイル期間にそれを**最も細かいCSS原子クラス**に分割する（一つのクラスは一つのプロパティのみを管理）、実行時は表を参照するだけ。**実行時のスタイル注入がない**——CSSは構築時に生成され、JSには一切のコストを要しない。実行時がなく、原子クラスがあり、型安全性がある。これら三つが合わさっている

## 戦略：まず共存し、その後分離する

100以上のファイルを一晩で変更することは不可能ですが、私は「双管線」戦略を使用しています。

**第一段階：2つのフレームワークが共存する。** TailwindとStyleXが同時に実装され、CSSの`@layer`によって順位が決定されます：

```css
@layer theme, base, components, priority1, ..., priority9, utilities;
```

StyleXの原子クラスが中央に位置しています（priority1-9がその領域です）。古いコンポーネントは引き続きTailwindを使用し、新しいコンポーネントはStyleXを使用し、それぞれが独立して機能します。

**第二段階：按目录分批搬家。** 133 個ファイルを 7 つの波に分け、各波ごとに一つの目録ごとに移動し、各波が終わったら即時に検査：タイプのチェック + 生産構築 + ブラウザでのページごとの実験。

**第三段階：終了。** 全ての移動が終わった後のある日の夜明けに、Tailwind の 5 つの依存を削除し、全てのカスタムツールを整理し、作業を終える。その後は以下の5つの問題の話。

## 問題記録（精選5つ）

### 問題1：`@stylex;` コマンドがTailwindに完全に飲み込まれた。

StyleXの構築には魔法の指示が必要です：CSS内に`@stylex;`を1行記述するだけです。

奇妙な事態が起こりました：設定はすべて正しく、構築も成功していますが、生成物には**一つの原子クラスもありません**。90分間調査した末、CSSの入り口のコンパイルプロセスをダンプして層ごと比較した結果、真相が明らかになりました：

Turbopackは各CSS入り口に対して**個別に**PostCSSプラグインチェーンを実行しますが、Tailwindがファイルを処理する際にはファイル全体を「再コンパイル」します。この過程で底層のコンパイラが知らない`@stylex;`をゴミとして処理してしまいます。指示が自分のファイル内に記述されているか、importされたかに関わらず、逃れることはできません。

**解決策**：`@stylex;`を独立した小さなCSS入り口に置き、このファイルはTailwindとは一切関わらず、指示はそのプラグインの手に渡ることができます。

### 坑二：两个来源的 stylex 类名，千万别用 cn() 拼合

これは実験と構建産物の二重証明です：

StyleXの統合意味は明確です——**同じ `stylex.props()` で後から書かれたものが先に書かれたものを上書きする**ため、上書きされた原子クラスは直接出力から削除されます。

しかし！二つの来源の stylex 类名を `cn()` 文字列で合わせると、衝突は「辞書順序」で解決されます——`padding: 12px` が `padding: 24px` になり、書いた順序は全く考慮されません。

**鉄律**：意味をカバーする場合は `stylex.props()` を同じ方法で使用する必要があります。`cn()` は外部のクラスを透過的に扱うためにのみ使用されます。

### 坑三：group-hoverの対処法は？マーカーが救世主です

Tailwindには「group-hover:」という便利な機能があります——親要素をホバーすると子要素が連動します。StyleXには祖先選択子がないため、この機能をどのように追加するのでしょうか？

答えは StyleX の marker メカニズムです：

```ts
// 1. 定義マーカー
export const hoverGroup = stylex.defineMarker()

// 2. コンテナにマーカーを追加（元の 'group' クラスを置き換える）
<div {...stylex.props(styles.wrap, hoverGroup)}>

// 3. 子要素に条件スタイルを使用
const styles = stylex.create({
  overlay: {
    opacity: {
      default: 0,
      [stylex.when.ancestor(':hover', hoverGroup)]: 1,
    },
  },
})
```

コンパイルされた核心ルールはおおよそ以下の通り：

```css
/* ホバー時に「最も近いマーカーを持つ祖先」にマスクが表示される */
.overlay:where(.marker:hover *) { opacity: 1; }
```

**意味と Tailwind の group-hover は完全に一致**——最も近いマーカーを持つ祖先のみを認識し、リスト内のホバーされたカードが同じ層の他のカードに影響を与えない。

また一つの意外な発見：原プロジェクトの監査を詳細に見ると、いくつかの場所でgroup-hoverは本来死んだコードだった（スタイルを持つ子要素がgroupコンテナに含まれておらず、リリース初日からは機能していなかった）。移行作業中に「ホイップオフ効果の検死」を行い、死んだものを埋めて、元のままの忠実性を保った。

### 罠四：Tailwindを削除する日、基礎も共に失われた

これが最も危険な部分だ。

Tailwindは、一面に広がるツール類の他に、サイト全体に**preflight**（基本リセット）を隠れて追加している：`box-sizing: border-box`、リンク色の継承、フォームのフォント継承、画像の`display: block`……すべて「感じないが、取り除くと問題が起きる」ようなものだ。

その夜はすべて正常に機能していた。翌日の検査時に初めて発見した：ブログのリストのタイトルが**ブラウザのデフォルトの青色下線リンク**になっている——詳しく調べると、全サイトの `box-sizing` も静かに `content-box` に戻っている。

このような回復は目でスクリーンショットを見ても全く分からない（ほとんどのコンポーネントのスタイルは明示的である）、新旧の二つのバージョンを**要素ごとの比較計算スタイル**で行った結果で明らかになった。修正方法：Tailwind v4 の preflight ソースコードを一行ずつ移植し、その中のTailwind独自の関数のみを交換する。

教訓：**何かを分解する前に先に問う——それは表面的な機能だけでなく、他に何を提供しているか？**

### 罠五：明るいと暗いの二種類の幽霊クラス名

- **明的**：Tailwindのスキャナーは**注釈内**のクラス名を真に受け取り、空でCSSを生成します。移行後、このクラスが根本的に解決されました——StyleXは注釈を読まない。  
- **暗的**：特殊効果コンポーネントのテキスト層は実行時に`document.createElement`で動的にクラス名が割り当てられる（JSXには含まれない）、そのためすべての静的スキャンでは見えない。Tailwindを削除した後、これら2つのクラス名は「未定義の空フリップ」になり、最終的には「実行時クラス名割り当て」モードで全データベースをスキャンすることで表示されるようになり、変更された。

一方は明らかに虚報、もう一方は暗に漏報——スキャナー式アプローチの2つの古典的な欠点が今回解決された。

## 成績表（正直な版）

| 指標 | 移行前 | 移行後 | 変化 |
|---|---|---|---|
| 主要CSS（raw） | 97.7 KB | 60.3 KB | **-38.3%** |
| 伝送量（gzip / brotli） | 17.8 / 14.5 KB | 14.9 / 12.9 KB | -16% / -11% |
| 最初のJS | 1246 KB | 1256 KB | +0.8%（ほとんど変わらない） |
| ビルド時間 | ~4s | ~4s | 変わらない |
| 実行時指標 | — | — | 変わらない |

ちょっと待って、なぜ raw の量が38%減少したのに、送信量は10〜16%しか減らないの？

なぜなら**コンパレーターとアトムの重複処理は「代替関係」であり、重複の累積関係ではない**からです：

- Tailwindの生成物の重複率が非常に高く、gzip/brotliが大部分の重複を処理できる（圧縮率6.8倍）
- StyleXのアトム表はコンパイル時点で既に重複が除去され、残りの内容の「エントロピー」が高いため、コンパレーターに処理できるものはほとんどない（4.7倍）

ですから、rawの-38%は「スタイルエンジンの効率向上」を示す正直な数字であり、送信の-10〜16%は「ユーザーが実際に節約したデータ量」です。二つの指標を別々に考える必要があります——**移行はスコア競争ではなく、rawの数字だけで送信を語ることはできない**のです。

実際の利益は見えない場所に隠されている：弱いネットワークと低スペックのデバイスでは、37 KBのCSSを少なくすることで、解析とメモリの節約が数十ミリ秒に相当し、さらに——**確実性**もある。

## 背景：この作業は「マルチエージェント」が担当している

今回のマイグレーションには面白い実行方法がある：133個のファイルを一つ一つ手書きするのではなく、自分が「総指揮官」としての役割を果たした。

- 迁移拆成工单：按目录分波次，每波派给并行的「迁移员」智能体，规则写死在工单里（对照编译产物取精确值、注释不许写 Tailwind 类名防止扫描器提取、禁止自己跑构建……）
- 每一波交付后我验收：`tsc` + 生产构建 + 浏览器逐页实测
- 还设了「审计员」角色：专门去原项目翻旧账，抓出「原版就死掉的代码」，避免把 bug 一起当遗产搬过来

最に魔幻なのは最後の倉庫切替えです。私はまだ「ローカルマージ、プッシュ、CI」の古典的なプロセスを想像していましたが、それが直接**クラウドへの変更**になります：新しいコミット履歴を強制的に遠隔端の `main` にプッシュし、ローカル倉庫の `fetch + reset` を引き戻します。Git Graphを開いてみると——え？どうしてまだ古い履歴が？まるで騙されたと思うところです。`git fetch`を実行すると、世界が静まります：

- `main` = 全新 StyleX 版（19 回のコミット）
- `archive/tailwind-v4` = 旧版の全歴史データ、同じリポジトリに保存されている保険
- 後悔薬：1つのコマンドでロールバックが可能

## 価値があるか？

宿題をコピーしたい人向けの正直なリストを提供する：

**価値がある、もしあなたが**：スタイルやボリュームに敏感で、プロジェクトが長期にわたって維持される必要があり、TypeScript を頻繁に使用し、余裕があれば（最も重要な点です）。

**ゆっくりと考える、もしあなたが**：Tailwind のエコシステムコンポーネントに重度依存している（shadcn のようなものをすぐに使う）、プロジェクトがリリースに近く、または単に小さなサイトを作りたい場合。

私にとって価値がある——38%のコストを節約するだけでなく、これからは「スタイルが間違ってもエラーが出ない」「注釈にあるクラス名が結果に含まれる」「このCSSはまだ使われているのか」といった幽霊問題に遭遇しない。スタイルはついに**型付きで、所有権があり、削除可能な**第一級のものになった。

> 97.7 KB → 60.3 KB。
> 133個のファイル、19回のコミット、0回のユーザーが気づく変更。
> これが最良のリファクリングの形かもしれません。
