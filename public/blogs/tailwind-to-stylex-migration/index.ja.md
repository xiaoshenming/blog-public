まず結論から話しましょう：今回、ブログ全体のスタイルシステムを Tailwind から StyleX に変更しました。21のルート、133のファイルの変更、19回のコミットがありました。メインスタイルシートは97.7 KBから60.3 KB（-38%）に減少し、構築時と実行時の状態はほとんど変わりませんでした。

**ブログ全体の様子——移行前と変わりません。**

全く同じであることが、今回の移行の最大の成功点です。

## なぜ有効だったTailwindを取り除くのか？

先自证清白：Tailwind は私に害を及ぼさない。非常に便利で、クラス名と文字列を JSX に貼り付けるだけで30分でページが作成される。私のブログはまさにそれによって育てられたものだ。

しかし、StyleXに夢中になっている。これはただの道具ではない。Meta製のもので、2020年にFacebook内部で開発され、2023年末にオープンソースになり、InstagramやWhatsAppの生産環境で5年間使用されている。それはTailwindとは異なる哲学である：

- **Tailwindは文字列の芸術**：`className="flex gap-2 px-4"`，見えるもの全てが実際に機能するが、間違いを犯しても誰も教えてくれない——スタイルはただ「静かに無効になる」だけだ。
- **StyleXはTypeScriptのオブジェクト**：`stylex.create({ ... })`，属性名や値を間違えても、`tsc`が即座にエラーを表示してくれる。

私を最も感動させた3点：

1. **型安全性**：スタイルが初めて型システムに組み込まれ、綴りの間違いが「反応なし」から「コンパイルエラー」に変わった
2. **確実性**：Tailwindはスキャナーで「どのクラスが使用されているか」を推測する——これには多くの謎が含まれる（テンプレストレーラーで作られたクラス名はスキャルできない、注釈にクラス名を書くと逆に生成物に含まれる）；StyleXはコンパイラが「どのスタイルが参照されているか」を知るため、推測がないので謎が生じない
3. **体重**：実際に参照される原子クラスのみを生成し、一つの値で全サイトで一つのクラスを使用する

もちろん、もっとシンプルな理由もある：ブログは私の実験場だ。それを実際に使わないのなら、会社のプロジェクトを使うのか？

ついでStyleXの仕組みについて言うと、実際は非常にシンプルだ：TSオブジェクトを書くと、コンパイル期間にそれを**最も細かいCSS原子クラス**に分割する（一つのクラスは一つのプロパティのみを管理する）、実行時はテーブルを検索する。**実行時のスタイル注入はない**——CSSは構築時に生成され、JSを一切消費しない。実行時がなく、原子クラスがあり、型安全性がある。これら三つが合わさって機能する

## 戦略：まず共存し、その後分離する

100以上のファイルを一晩で変更することは不可能ですが、私が使用しているのは「双管線」戦略です。

**第一段階：2つのフレームワークが共存する。** TailwindとStyleXが同時に実装され、CSSの`@layer`によって順位が決定されます：

```css
@layer theme, base, components, priority1, ..., priority9, utilities;
```

StyleXの原子クラスが中央に位置しています（priority1-9がその領域です）。古いコンポーネントは引き続きTailwindを使用し、新しいコンポーネントはStyleXを採用し、それぞれが独立して機能します。

**第二段階：按目录分批搬家。** 133 個ファイルを 7 つの波に分け、各波ごとに一つの目録に従って、各波が完了したら即時に検査：タイプのチェック + 生産構築 + ブラウザでのページごとの実験。

**第三段階：終了。** 全ての移動が終わった後のある日の早朝、Tailwind の 5 つの依存を削除し、全てのカスタムツールを整理し、作業を終える。その後は以下の五つの問題の話だ。

## 問題記録（五つを選出）

### 問題一：`@stylex;` コマンドがTailwindに完全に飲み込まれた

StyleXの構築には魔法の命令が必要です：CSS内に`@stylex;`を1行記述するだけです。

奇妙な事態が起こりました：設定はすべて正しく、構築も成功していますが、生成物には**一つの原子クラスもありません**。90分間調査した末、CSSの入口のコンパイルプロセスをダンプして層ごとに比較した結果、真実が明らかになりました：

Turbopackは各CSS入口に対して**個別に**PostCSSプラグインチェーンを実行しますが、Tailwindがファイルを処理する際にはファイル全体を「再コンパイル」します。この過程で底層のコンパイラが知らない`@stylex;`をゴミとして処理してしまいます。命令が自分のファイル内に記述されているか、importされたかに関わらず、逃れることはできません。

**解決策**：`@stylex;`を独立した小さなCSS入口に置き、このファイルはTailwindとは全く関わらず、命令はそれを読むプラグインの手に渡ります。

### 坑二：两个来源的 stylex 类名，千万别用 cn() 拼

これは実験と構築産物の二重証明です：

StyleXの統合意味は明確です——**同じ `stylex.props()` で、後から書かれたものが先に書かれたものを上書きする**ため、上書きされた原子クラスは直接出力から削除されます。

しかし！もし二つの来源の stylex 类名を `cn()` 文字列で連結すると、衝突は「辞書順序」で解決されます——`padding: 12px` が `padding: 24px` に変わり、書いた順番は全く意味を持ちません。

**鉄律**：意味をカバーする場合は `stylex.props()` を同じ方法で使用し、`cn()` は外部のクラスを透過伝播するためにのみ使用される。

### 坑三：group-hover の対処法は？マーカーが救世主です

Tailwindには`group-hover:`という便利な機能があります——親要素にホバーがかかったとき、子要素が連動します。StyleXには祖先選択子がないため、この機能をどのように追加するのでしょうか？

答えは StyleX の marker メカニズムです：

```ts
// 1. 定義マーカー
export const hoverGroup = stylex.defineMarker()

// 2. コンテナにマーカーを追加（元の 'group' クラスに代わるもの）
<div {...stylex.props(styles.wrap, hoverGroup)}>

// 3. 子要素に条件スタイルを使用
const styles = stylex.create({
  overlay: {
    opacity: {
      default: 0,
      [stylex.when.ancestor(':hover', hoverGroup)]: 1,
    },
  },
})
```

コンパイルされた核心ルールはおおよそ以下の通り：

```css
/* ホバー時に「最も近いマーカーを持つ祖先」にマスクが表示される */
.overlay:where(.marker:hover *) { opacity: 1; }
```

**セマンティクスは Tailwind の group-hover と完全に一致**——最近のマーカーを持つ祖先のみを認識し、リスト内でホバーしたカードが同じ層の他のカードに影響を与えない。

また一つの意外な発見があります：原プロジェクトの監査を詳細に見てみると、いくつかの場所でgroup-hoverは本来死んだコードでした（スタイルを持つ子要素がgroupコンテナに含まれておらず、リリース初日からは機能していませんでした）。移行作業中に「ホイップオフ効果の検死」をして、死んだものを埋め合わせました。元のまま保証しています。

### 罠四：Tailwindを解体する日、基礎も共に失われた

これが最も危険な部分です。

Tailwindには一面に広がるツール類がありますが、こっそりと全サイトに**preflight**（基本リセット）を追加しています：`box-sizing: border-box`、リンク色の継承、フォームのフォント継承、画像の`display: block`……すべて「感じないけど、取り除けば問題が起きる」ようなものです。

# 基礎も共に失われた

その夜はすべて正常に機能していた。翌日の検査時に初めて発見した：ブログのリストのタイトルが**ブラウザのデフォルトの青色下線リンク**になっていた——詳しく調べてみると、全サイトの `box-sizing` もこっそりと `content-box` に戻っていた。

このような回帰は肉眼でスクリーンショットを見ても全く分からない（ほとんどのコンポーネントのスタイルは明示的である）。新旧の二つのバージョンを**要素ごとの比較計算スタイル**で行ったことで初めて明らかになった。修正方法：Tailwind v4のpreflightコードを一行ずつ移植し、その中のTailwind独自の関数のみを交換する。

教訓：**何かを分解する前に先に問いかけよ——表面的な機能以外に、何を提供しているのか？**

### 罠五：一明一暗、二種類の幽霊クラス名

- **明的**：Tailwindのスキャナーは**注釈内**のクラス名を真に受け入れ、空でCSSを生成します。移行後、このクラスは完全に解決されました——StyleXは注釈を読まない。
- **暗的**：特定の効果要素のテキスト層は実行時に`document.createElement`で動的にクラス名を割り当てるものです（JSXには含まれていません）。すべての静的スキャンでは見えません。Tailwindを削除した後、これら2つのクラス名は「定義されていない空フリップ」になり、最終的には「実行時クラス名割り当て」モードで全データベースをスキャンすることで表示され、変更されました。

明らかな虚報と暗い漏報——スキャナー式アプローチの2つの典型的な欠点が、今回は解決されました。

## 成績表（正直な版）

| 指標 | 移行前 | 移行後 | 変化 |
|---|---|---|---|
| 主要CSS（raw） | 97.7 KB | 60.3 KB | **-38.3%** |
| 伝送量（gzip / brotli） | 17.8 / 14.5 KB | 14.9 / 12.9 KB | -16% / -11% |
| 最初のJS | 1246 KB | 1256 KB | +0.8%（ほとんど変わらない） |
| ビルド時間 | ~4s | ~4s | 変わらない |
| 実行時指標 | — | — | 変わらない |

待ってください、なぜ raw の減少が 38%になり、送信量は 10~16%しか減っていないのですか？

なぜなら**コンパレーターとアトムの重複処理は「代替関係」であり、重複の累積ではない**からです：

- Tailwindの生成物は重複率が高く、gzip/brotliが大部分の重複を処理できる（圧縮率は6.8倍）
- StyleXのアトム表はコンパイル時には既に重複が除去されており、残りの内容の「エントロピー」が高いため、コンパレーターに処理できるものはほとんどない（4.7倍）

したがって、rawの-38%は「スタイルエンジンの効率向上」の客観的な数字であり、送信の-10~16%は「ユーザーが実際に節約したトラフィック」です。二つの指標を別々に説明する必要があります——**移行はスコア競争ではなく、rawの数字で送信を誇張することはできない**です。

実際の利益は見えない場所に隠されている：弱いネットワークと低スペックの端末では、37 KBのCSSが少なくなることで、解析とメモリの節約が数十ミリ秒にもなる；そして——**確実性**もある。

## 背景：この作業は「マルチエージェント」が担当している

今回のマイグレーションには面白い実行方法がある：133個のファイルを一つ一つ手書きするのではなく、私が「総指揮官」としての役割を果たした。

- マイグレーションを作業タスクに分割：ディレクトリに基づいてフェーズに分け、各フェーズを並行する「マイグレーション担当者」エージェントに割り当てる。ルールは作業タスクに固定されている（コンパイル結果を参照して正確な値を取得、注釈にはTailwindのクラス名を入れないようにしてスキャナーを防ぎ、自己構築を禁止するなど）
- 各フェーズが完了した後、私が検収：`tsc`による検査 + 実際の構築 + ブラウザでのページごとのテスト
- 「監査員」という役割も設定：元のプロジェクトから古いデータを調査し、「元のバージョンで死んだコード」を特定し、バグを一緒に引き継ぐことを防ぐ

- 留仙洞 → Liuxiandong
- 鸣潮 → Wuthering Waves
- 博主/站名 Suni → Suni
- 汇文明朝体 → Huiwen Mingcho (font name)

最魔幻的是收尾的仓库切换。我还在脑补「本地合并、推送、CI」的经典流程，它直接来了手**云端换血**：把新的提交历史强制推送成远端 `main`，再把本地仓库 `fetch + reset` 过来。我打开 Git Graph 一看——诶？怎么还是旧历史？差点以为被耍了。`git fetch` 一下，世界安静了：

- `main` = 全新 StyleX 版（19 次提交）
- `archive/tailwind-v4` = 旧版全部历史，同一个仓库里躺着当保险
- 后悔药：一条命令回滚

## 值不值得？

给想抄作业的人一个诚实清单：

**価値がある、もしあなたが**：スタイルやサイズに敏感で、プロジェクトが長期にわたって維持される必要があり、TypeScript を頻繁に使用し、余裕があれば（最も重要な点です）。

**ゆっくりと考える、もしあなたが**：Tailwind のエコシステムコンポーネントに頼りがり（shadcn のようなすぐ使えるもの）、プロジェクトがリリースに近く、または単に小さなサイトを作りたい場合。

私にとって価値がある——38%のコストを節約できるだけでなく、これからは「スタイルが間違ってもエラーが出ない」「注釈のクラス名が結果に含まれる」「このCSSはまだ使われているのか」といった幽霊問題に遭遇しない。スタイルはついに**型付きで、所有権があり、削除可能な**第一級のものになった。

> 97.7 KB → 60.3 KB。
> 133個のファイル、19回のコミット、0人のユーザーが気づく変更。
> これが再構築の最良の形かもしれません。
