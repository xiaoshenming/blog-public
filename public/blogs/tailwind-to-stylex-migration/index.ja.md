まず結論から言う：今回、ブログ全体のスタイルシステムを Tailwind から StyleX に変更した。21のルート、133のファイルの変更、19回のコミット。メインスタイルシートは97.7 KBから60.3 KB（-38%）に減少した。構築時と実行時の動作は……ほとんど変わっていない。

**ブログ全体の様子——移行前と全く同じです。**

全く同じであることが、今回の移行の最大の成功点である。

## なぜ有効だったTailwindを削除するのか？

先自证清白：Tailwind は私に害を及ぼさない。非常に便利で、クラス名と文字列を JSX に貼り付けるだけで30分でページが作成される。私のブログはまさにそれによって育てられたものだ。

しかし、StyleXに夢中になっている。これはただのツールではない。Meta製であり、2020年にFacebook内部で開発され、2023年末にオープンソースになり、InstagramやWhatsAppの生産環境で5年間使用されている。これはTailwindとは異なる哲学だ。

- **Tailwindは文字列の芸術**：`className="flex gap-2 px-4"`，見えるもの全てが反映されるが、間違いを犯しても誰も教えてくれない——スタイルはただ「静かに機能しない」だけだ。
- **StyleXはTypeScriptのオブジェクト**：`stylex.create({ ... })`、属性名や値の間違いを`tsc`が即座に指摘する。

私を最も感動させた3点：

1. **型安全性**：スタイルが初めて型システムに組み込まれ、綴りの間違いが「反応なし」から「コンパイルエラー」に変わった
2. **確実性**：Tailwindはスキャナーで「どのクラスが使用されているか」を推測する——これには多くの神秘的な要素がある（テンプレート文字列で作られたクラス名はスキャルできない、注釈にクラス名を書くと逆にプロダクトに含まれる）；StyleXはコンパイラが「どのスタイルが参照されているか」を知っているため、推測がないので神秘的な要素がない
3. **体重**：実際に参照される原子クラスのみを生成し、一つの値で全サイトで一つのクラスを使用する

もちろん、もっとシンプルな理由もある：ブログは私の実験場だ。それを畑に使わないのなら、会社のプロジェクトを使うのか？

ついでStyleXの仕組みについて言うと、実は非常にシンプルだ：TSオブジェクトを書くと、コンパイル時にそれを**最も細かいCSS原子クラス**に分割する（一つのクラスは一つのプロパティのみを管理する）、実行時は表を参照する。**実行時のスタイル注入はない**——CSSは構築時に生成されるため、JSには一切のコストを要しない。実行時がなければ、原子クラス、型安全性が実現される。これら三つが合わさって機能する

## 戦略：まず共存し、その後分離する

100以上のファイルを一晩で変更することは不可能ですが、私が使用しているのは「双管線」戦略です。

**第一段階：2つのフレームワークが共存する。** TailwindとStyleXが同時に実装され、CSSの`@layer`によって順位が決まります：

```css
@layer theme, base, components, priority1, ..., priority9, utilities;
```

StyleXの原子クラスが中央に位置しています（priority1-9がその領域です）。古いコンポーネントは引き続きTailwindを使用し、新しいコンポーネントはStyleXを採用し、それぞれが独立して機能します。

**第二段階：按目录分批搬家。** 133 個ファイルを 7 つの波に分け、各波ごとに一つの目録に従って、各波が完了したら即時に検査：タイプのチェック + 生産構築 + ブラウザでのページごとの実測。

**第三段階：終了。** 全ての移動が終わった後のある日の早朝、Tailwind の 5 つの依存を削除し、全てのカスタムツールを削除し、作業を終える。その後は以下の5つの問題の話。

## 問題記録（5つを選出）

### 問題1：`@stylex;` 指令がTailwindに完全に飲み込まれた

StyleXの構築には魔法の指示が必要です：CSSに一行`@stylex;`を書くだけです。

奇妙な事態が起こりました：設定はすべて正しく、構築も成功していますが、生成物には**一つの原子クラスもありません**。90分間調査した末、CSSの入口のコンパイルプロセスをダンプして層ごとに比較した結果、真実が明らかになりました：

Turbopackは各CSS入口に対して**個別に**PostCSSプラグインチェーンを実行しますが、Tailwindがファイルを処理する際にはファイル全体を「再コンパイル」します。この過程で下層コンパイラが知らない`@stylex;`をゴミとして処理します。指示が自分のファイル内に書かれていても、importされたものであっても、逃れることはできません。

**解決策**：`@stylex;`を独立した小さなCSS入口に置き、このファイルはTailwindとは全く関わらず、指示はそのプラグインの手に渡ります。

### 坑二：两个来源的 stylex 类名，千万别用 cn() 拼

これは実験と構築産物の二重証明です：

StyleXの統合意味は明確です——**同じ `stylex.props()` で、後から書かれたものが先に書かれたものを上書きする**ため、上書きされた原子クラスは直接出力から削除されます。

しかし！もし二つの来源の stylex 类名を `cn()` 文字列で連結すると、衝突は「辞書順序」で解決されます——`padding: 12px` が `padding: 24px` に変わり、書いた順番は全く意味を持ちません。

**鉄律**：意味内容をカバーする場合、`stylex.props()`を同じ方法で使用する必要があり、`cn()`は外部のクラスを透過表示するためにのみ使用される。

### 坑三：group-hover はどう対処する？マーカーが救急隊

Tailwindには`group-hover:`という優れた機能がある——親要素をホバーすると子要素が連動する。StyleXには祖先選択子がないので、この機能をどう実装するか？

答えはStyleXのマーカー機構だ：

```ts
// 1. 定義マーカー
export const hoverGroup = stylex.defineMarker()

// 2. コンテナにマーカーを追加（元の 'group' クラスに代わる）
<div {...stylex.props(styles.wrap, hoverGroup)}>

// 3. 子要素用条件スタイル
const styles = stylex.create({
  overlay: {
    opacity: {
      default: 0,
      [stylex.when.ancestor(':hover', hoverGroup)]: 1,
    },
  },
})
```

コンパイルされた核心ルールはおおよそ以下の通り：

```css
/* ホバー時、最も近いマーカーを持つ祖先にマスクが表示される */
.overlay:where(.marker:hover *) { opacity: 1; }
```

**セマンティクスは Tailwind の group-hover と完全に一致**——最も近いマーカーを持つ祖先のみを認識し、リスト内のカードをホバーすると同層の他のカードが影響を受けない。

また一つの意外な発見がありました：原プロジェクトの監査を詳細に見ると、**いくつかの場所で group-hoverは本来死んだコードでした**（スタイルを持つ子要素が groupコンテナに含まれておらず、公開初日からは機能していませんでした）。移行作業中に「ホイップ効果の検死」を行い、死んだものは処理し、元のまま保証しました。

### 罠四：Tailwindを解体する日、基礎も共に失われた

これが最も危険なものです。

Tailwindは、一面に広がるツール類の他に、こっそりと全サイトに **preflight**（基本リセット）を追加しました：`box-sizing: border-box`、リンク色の継承、フォームのフォント継承、画像の `display: block`……すべて「感覚上ではないが、取り除くと問題が起きる」ようなものです。

# グループホイップの問題点

その夜は何も問題なく機能していた。翌日の巡回検査時に初めて発見した：ブログのリストのタイトルが**ブラウザのデフォルトの青色下線リンク**になっていた——詳細を調べてみると、全サイトの `box-sizing` も静かに `content-box` に戻っていた。

このような回復は目でスクリーンショットを見ても全く分からない（ほとんどのコンポーネントのスタイルは明示的である）、新旧の二つのバージョンを**要素ごとの比較計算スタイル**で行った時に初めて明らかになった。修正方法：Tailwind v4 の preflight ソースコードを一行ずつ移植し、その中の Tailwind独自の関数のみを交換する。

教訓：**何かを分解する前に先に問い——表面的な機能以外に、何を提供しているのか？**

### 罠五：一明一暗、二種類の幽霊クラス名

- **明的**：Tailwindのスキャナーは**注釈内**のクラス名を真に受け入れ、空でCSSを生成します。移行後、このクラスが根本的に解決されました——StyleXは注釈を読まない。
- **暗的**：特定の効果要素のテキスト層は実行時に`document.createElement`で動的にクラス名を割り当てるものです（JSXには含まれていません）。すべての静的スキャンでは見えません。Tailwindを削除した後、これら2つのクラス名は「定義されていない空値」になり、最終的には「実行時クラス名割り当て」モードで全データベースをスキャンすることで表示され、変更されました。

一方は明らかに虚報、もう一方は暗に漏報——スキャナー式アプローチの2つの典型的な欠点が今回は解決されました。

## 成績表（正直な版）

| 指標 | 移行前 | 移行後 | 変化 |
|---|---|---|---|
| 主要CSS（raw） | 97.7 KB | 60.3 KB | **-38.3%** |
| 伝送量（gzip / brotli） | 17.8 / 14.5 KB | 14.9 / 12.9 KB | -16% / -11% |
| 最初のJS | 1246 KB | 1256 KB | +0.8%（ほとんど変わらない） |
| ビルド時間 | ~4s | ~4s | 変わらない |
| 実行時指標 | — | — | 変わらない |

待ってください、なぜ raw の減少が 38%になり、送信量が 10〜16%しか減らないのでしょうか？

なぜなら**コンパレーターとアトムの重複は「代替関係」であり、重複する関係ではない**からです：

- Tailwindの成果物は重複率が非常に高く、gzip/brotliが大部分の冗長データを削除できる（圧縮率は6.8倍）
- StyleXのアトム表はコンパイル時点で既に重複が解消されており、残りの内容の「エントロピー」が高いため、コンパレーターには何も削除できない（4.7倍）

したがって、rawの-38%は「スタイルエンジンの効率向上」を示す正直な数字であり、送信の-10〜16%は「ユーザーが実際に節約したデータ量」です。二つの指標を別々に説明する必要があります——**移行はスコア競争ではなく、rawの数字で送信を誇張することはない**です。

実際の利益は見えない場所に隠されている：弱いネットワークと低スペックのマシンでは、37 KBのCSSを少なくすることで、解析とメモリの節約が約数十ミリ秒にもなる；そして——**確実性**もある。

## 背景：この作業は「マルチエージェント」が行う

今回のマイグレーションには面白い実行方法がある：133個のファイルを一つ一つ手書きするのではなく、私が「総指揮官」としての役割を果たした。

- マイグレーションを作業タスクに分割：ディレクトリに基づいてフェーズに分け、各フェーズを並行する「マイグレーション担当」エージェントに割り当てる。ルールは作業タスクに固定されている（コンパイル結果を参照して正確な値を取得、注釈にはTailwindのクラス名を入れないようにしてスキャナーを防ぎ、自己構築を禁止するなど）
- 各フェーズが完了した後、私が検収：`tsc` + プロダクション構築 + ブラウザでのページごとのテスト
- 「監査員」という役割も設定：元プロジェクトから古いデータを調査し、「元のバージョンで死んだコード」を特定し、バグを一緒に引き継ぐことを防ぐ

- 留仙洞 → Liuxiandong
- 鸣潮 → Wuthering Waves
- 博主/站名 Suni → Suni
- 汇文明朝体 → Huiwen Mingcho (font name)

最魔幻的是收尾的仓库切换。我还在脑补「本地合并、推送、CI」的经典流程，它直接来了手**云端换血**：把新的提交历史强制推送成远端 `main`，再把本地仓库 `fetch + reset` 过来。我打开 Git Graph 一看——诶？怎么还是旧历史？差点以为被耍了。`git fetch` 一下，世界安静了：

- `main` = 全新 StyleX 版（19 次提交）
- `archive/tailwind-v4` = 旧版全部历史，同一个仓库里躺着当保险
- 后悔药：一条命令回滚

## 值不值得？

给想抄作业的人一个诚实清单：

**価値がある、もしあなたが**：スタイルやサイズに敏感で、プロジェクトが長期にわたって維持される必要があり、TypeScript を頻繁に使用し、余裕があれば（最も重要な点）。

**ゆっくりと考える、もしあなたが**：Tailwind のエコシステムコンポーネントに重度依存しており（shadcn のようなものをすぐに使う）、プロジェクトがリリースに近く、または単に小さなサイトを作りたいだけなら。

私にとっては価値がある——38%のコストを節約するだけでなく、これからは「スタイルが間違ってもエラーが出ない」「注釈のクラス名が成果物に混入される」「このCSSは本当にまだ使われているのか」といった幽霊問題に遭遇しない。スタイルはついに**型付きで、所有権があり、削除可能な**第一級のものになった。

> 97.7 KB → 60.3 KB。
> 133ファイル、19回のコミット、0人のユーザーが気づく変更。
> これがおそらくリファクリの最良の形だ。
