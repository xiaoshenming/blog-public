먼저 결론부터 말하자면, 이번에 전체 블로그의 스타일 체계를 Tailwind에서 StyleX로 바꿨습니다. 21개의 라우트, 133개의 파일 변경, 19번의 커밍دم. 메인 스타일 시트는 97.7 KB에서 60.3 KB로 (-38%) 줄어들었으며, 빌드와 실행 과정은 거의 변하지 않았습니다.

**전체 블로그의 모습이 이렇습니다—마이그레이션 전과 똑같습니다.**

완벽한 유사성이 이번 마이그레이션의 가장 큰 성과입니다.

## 왜 잘 작동하는 Tailwind을 버려야 하는가?

먼저 정당성을 증명하자: Tailwind은 나를 괴롭히지 않았다. 매우 유용해서 클래스명과 문자열을 JSX에 붙이기만 하면 30분 만에 페이지가 만들어진다. 내 블로그는 바로 이걸로 성장했다.

하지만 나는 StyleX에 오랫동안 갈망했다—이것은 원치 않는 것이 아니라 Meta에서 만든 제품이다: 2020년에 Facebook 내부에서 시작되어 2023년 말에 오픈소스로 공개되었으며, Instagram과 WhatsApp의 생산 환경에서 5년 동안 사용되었다. 이는 Tailwind과는 다른 철학이다:

- **Tailwind은 문자열 예술**: `className="flex gap-2 px-4"`, 보는 즉시 결과가 나오지만 잘못된 값을 넣어도 아무 말도 하지 않는다—스타일은 그저 "조용히 작동하지 않는다"
- **StyleX는 TypeScript 객체**: `stylex.create({ ... })`, 속성 이름을 잘못 입력하거나 값을 잘못 넣으면 `tsc`가 바로 오류를 보여준다

내가 가장 감동한 세 가지:

1. **타입 안전성**：스타일이 처음으로 타입 시스템에 편입되면서 철자 오류가 «무반응»에서 «컴파일 에러»로 바뀌었습니다.  
2. **확실성**：Tailwind은 스캐너를 이용해 «어떤 클래스가 사용되었는지»를 추측합니다 — 이에는 많은 신비한 요소가 있습니다(템플릿 문자열로 만들어진 클래스명은 스캔할 수 없으며, 주석에 클래스명을 적으면 오히려 결과물에 포함됩니다); StyleX는 컴파일러가 «어떤 스타일이 참조되었는지»를 알기 때문에 추측 없이 신비한 요소도 없습니다.  
3. **체중**：실제로 참조된 원자 클래스만 생성하며, 한 값에 전체 사이트에서 한 클래스를 사용합니다.

물론, 더 단순한 이유도 있습니다: 블로그는 제 실험장입니다. 이를 땅에 내지 않으면 회사 프로젝트를 사용할까요?

덧붙이자면 StyleX의 원리는 매우 단순합니다: TS 객체를 작성하면 컴파일 단계에서 이를 **가장 세분화된 CSS 원자 클래스**로 분해합니다(한 클래스는 한 속성만 관리합니다); 실행 시에는 테이블 검색이 됩니다.**실행 시 스타일 삽입이 없습니다** — CSS는 빌드 단계에서 이미 생성되어 JS에 아무 비용도 들지 않습니다. 실행 시 없음, 원자 클래스, 타입 안전성 — 이 세 가지가 합쳐져서 작동합니다.

## 전략: 먼저 공존하고, 나중에 분리합니다

100여 개의 파일을 하룻밤에 바꿀 수는 없으므로, 저는 「이중 라인 구조」 전략을 사용합니다.

**1단계: 두 프레임이 평화롭게 공존합니다.** Tailwind과 StyleX가 동시에 사용되며, CSS의 `@layer`를 이용해 순서를 정합니다:

```css
@layer theme, base, components, priority1, ..., priority9, utilities;
```

StyleX의 아том 클래스가 중간에 위치합니다(priority1-9은 그들의 영역), 기존 컴포넌트는 여전히 Tailwind을 사용하고, 새로운 컴포넌트는 StyleX를 사용하여 각자의 역할을 수행합니다.

**2단계: 디렉터리별로 파일을 분할하여 이동합니다.** 133개의 파일을 7개의 단계로 나누어, 각 디렉터리별로 한 번에 이동하며, 각 단계가 완료되면 현장에서 검수를 진행합니다: 유형 확인 + 생산 구축 + 브라우저를 이용한 페이지 단계별 테스트.

**3단계: 마무리.** 모든 파일이 이동이 완료된 후의 어느 날 새벽에 Tailwind의 5개 의존성을 삭제하고 모든 커스텀 도구를 정리한 후 작업을 종료합니다. 그 다음은 아래 다섯 가지 문제에 대한 이야기입니다.

## 실수 기록 (다섯 가지를 선별)

### 실수 1: `@stylex;` 명령어가 Tailwind에 완전히 삭제되었습니다.

StyleX의 구축에는 마법적 명령어가 필요합니다: CSS에 `@stylex;` 한 줄을 작성하면 됩니다.

이상한 일이 발생했습니다: 설정은 완벽하고 구축도 성공적이지만 결과물에는 **하나의 원소 클래스도 없습니다**. 90분 동안 조사했으나, 결국 CSS 인터페이스의 컴파일 과정을 출력하여 단계별 비교한 끝에 진실을 발견했습니다:

Turbopack은 각 CSS 인터페이스에 대해 **개별적으로** PostCSS 플러그인 체인을 실행합니다. Tailwind은 파일을 처리할 때 전체 파일을 «다시 컴파일»하므로, 이 과정에서 기반 컴파일러는 알지 못하는 `@stylex;`을 쓰레기로 처리합니다. 명령어는 자신이 작성한 파일에 있든 import된 파일에 있든 피할 수 없습니다.

**해결 방법**: `@stylex;`을 독립적인 작은 CSS 인터페이스에 넣으세요. 이 파일은 Tailwind과는 상관없이, 명령어는 해당 파일을 처리하는 플러그인에 의해 처리됩니다.

### 坑二：두 출처의 stylex 클래스명을 사용할 때는 절대로 cn()로 조합하지 마세요

이것은 실험 및 빌드 결과를 통한 두 가지 증거로 구성된 내용입니다:

StyleX의 합성 의미는 명확합니다—**동일한 `stylex.props()`에서 뒤에 있는 값이 앞에 있는 값을 덮는** 방식으로, 덮인 애노틱 클래스는 출력에서 직접 제거됩니다.

하지만! 두 출처의 stylex 클래스명을 `cn()` 문자열로 조합하면 충돌이 "사전 순서"에 따라 해결됩니다—`padding: 12px`가 `padding: 24px`로 처리되며, 당신이 정한 순서는 전혀 중요하지 않습니다.

**철률**：의미를 커버하는 경우 `stylex.props()`를 반드시 같은 방식으로 사용해야 합니다. `cn()`는 외부 클래스의 데이터를 전달하는 용도로만 사용됩니다.

### 함정 3: group-hover는 어떻게 처리하나요? 마커가 해결책입니다

Tailwind에는 `group-hover:`라는 강력한 기능이 있습니다. 부모 요소를 마우스 오버 시 자식 요소가 연동됩니다. StyleX에는 조상 선택기가 없어서 이 기능을 어떻게 적용할 수 있을까요?

답은 StyleX의 마커 메커니즘입니다.

```ts
// 1. 마커를 정의합니다
export const hoverGroup = stylex.defineMarker()

// 2. 컨테이너에 마커를 추가하여 기존의 'group' 클래스를 대체합니다
<div {...stylex.props(styles.wrap, hoverGroup)}>

// 3. 하위 요소에 조건 스타일을 적용합니다
const styles = stylex.create({
  overlay: {
    opacity: {
      default: 0,
      [stylex.when.ancestor(':hover', hoverGroup)]: 1,
    },
  },
})
```

컴파일된 핵심 규칙은 대략 다음과 같습니다:

```css
/* 마커가 있는 가장 가까운 조상에 마우스를 올렸을 때 마스킹이 나타납니다 */
.overlay:where(.marker:hover *) { opacity: 1; }
```

**의미와 Tailwind의 group-hover는 완벽하게 일치합니다**——가장 가까운 마커 조상을 인식하며, 목록 내에서 마커가 있는 카드에 마우스를 올리면 같은 레벨의 다른 카드가 영향을 받지 않습니다.

추가적인 놀라운 발견도 있었습니다: 원본 프로젝트의 감사에서 확인한 바에 따르면, **여러 곳에서 group-hover가 사실은 죽은 코드였습니다** (스타일을 가진 하위 요소가 group 컨테이너 안에 없어서 출시 첫날부터 아무런 효과도 없었습니다). 마이그레이션할 때 간단히 「悬停 효과 조사」를 했고, 죽은 것들은 처리했으며, 원래대로 보존했습니다.

### 네 번째 문제: Tailwind을 분리할 때, 기반도 함께 사라졌습니다

이것이 가장 위험한 부분입니다.

Tailwind은 화면 가득한 도구들 외에도, 전체 사이트에 **preflight**라는 층을 숨김으로써 제공합니다: `box-sizing: border-box`, 링크 색상의 상속, 형태체재의 상속, 이미지의 `display: block` 등… 모두 "당신은 그것을 느끼지 못하지만, 제거하면 문제가 생기는" 것들입니다.

그날 밤 모든 것이 정상했지만, 다음 날 점검할 때야 블로그 목록의 제목이 **브라우저의 기본 파란색 하이퍼링크**로 변했음을 발견했다. 다시 확인해보니 전체 사이트의 `box-sizing`도 조용히 `content-box`로 돌아왔다.

이런 복귀는 눈으로 스크린샷을 보아도 전혀 알 수 없다(대부분의 컴포넌트 스타일은 명확하게 표시된다). 이는 오래된 버전과 새로운 버전을 **요소별로 비교하여 스타일을 계산**한 결과로 밝혀졌다. 수정 방법은 Tailwind v4의 preflight 소스 코드를 한 줄 한 줄 이식하여, 그 안의 Tailwind 고유 함수만 교체하는 것이다.

교훈: **무언가를 분해하기 전에 먼저 물어보세요—표면적인 기능 외에 무엇을 제공하는지도 알아야 합니다.**

### 함정 5: 한쪽은 밝고 다른 한쪽은 어두운, 두 가지 유형의 유령 클래스명

- **明的**：Tailwind의 스캐너는 **주석 내**의 클래스명을 진지하게 받아들여 CSS을 생성합니다. 마이그레이션 후 이 클래스는 완전히 해결되었으며, StyleX는 주석을 읽지 않습니다.
- **暗的**：특수 효과 컴포넌트의 텍스트 레이어는 실행 시 `document.createElement`으로 동적으로 클래스명을 할당하는데 (JSX에는 없습니다), 모든 정적 스캐너에서는 이를 볼 수 없습니다. Tailwind을 분리한 후 이 두 클래스명은 «정의되지 않은 공백»이 되고, 마지막으로 «실행 시 클래스명 할당» 모드로 전체 라이브러리를 스캔해야만 발견됩니다, 수정되었습니다.

한 가지는 노골적으로 과다 보고하고, 다른 하나는 은밀하게 과소 보고—스캐너 방식의 방안의 두 가지 고전적인 단점이 이번에는 해결되었습니다.

## 성적표 (정직 버전)

| 지표 | 마이그레이션 전 | 마이그레이션 후 | 변화 |
|---|---|---|---|
| 주 CSS (raw) | 97.7 KB | 60.3 KB | **-38.3%** |
| 전송량 (gzip / brotli) | 17.8 / 14.5 KB | 14.9 / 12.9 KB | -16% / -11% |
| 첫 페이지 JS | 1246 KB | 1256 KB | +0.8% (거의 변동 없음) |
| 빌드 시간 | ~4s | ~4s | 변동 없음 |
| 실행 시 지표 | — | — | 변동 없음 |

잠깐, 왜 raw의 감소율이 38%인데 전송량은 10~16%만 감소했나요?

왜냐하면 **압축기와 원자 데이터는 '대체 관계'이지, 중첩 관계가 아니기 때문입니다**:

- Tailwind의 결과물은 중복률이 매우 높아서 gzip/brotli가 대부분의 중복 데이터를 처리할 수 있습니다(압축율 6.8배)
- StyleX의 원자 테이블은 컴파일 단계에서 이미 중복된 데이터가 제거되었고, 남은 내용의 '엔트로피'가 더 높아서 압축기가 더 이상 처리할 수 있는 것이 없습니다(4.7배)

그러므로 raw -38%는 '스타일 엔진의 효율 향상'에 대한 정직한 수치이며, 전송 -10~16%는 '사용자가 실제로 절약한 트래픽'입니다. 두 측정 기준을 별도로 설명해야 합니다 – **마이그레이션은 점수 경기가 아닌데, raw 수치를 가지고 전송을 과장하지 마세요.**

보이지 않는 곳에 진짜 이익이 숨겨져 있습니다: 약한 네트워크와 저급 기기에서 CSS 파일 크기가 37 KB 줄어들면 해석 및 메모리 사용 시간이 수십 마이크로초 절약됩니다; 그리고——**결정성**도 있습니다.

## 뒤에서: 이 작업은 «다중agent»가 수행합니다

이번 마이그레이션에는 재미있는 실행 방식이 있습니다: 저는 133개의 파일을 한 줄 한 줄 손으로 작성하지 않았으며, 대신 «총지휘자» 역할을 했습니다.

- 마이그레이션을 작업 목록으로 나누었습니다: 디렉터리에 따라 여러 단계로 나누고, 각 단계는 병행되는 «마이그레이션 담당자» 에이전트에게 배정됩니다. 규칙은 작업 목록에 명시되어 있습니다 (컴파일된 결과물과 비교하여 정확한 값을 가져오기, 주석에는 Tailwind 클래스명을 넣지 말고 스캐너를 방지하기 위해, 자체 빌드를 금지하는 등)
- 각 단계가 전달된 후 저는 검수를 합니다: `tsc` + 배포 빌드 + 브라우저에서 페이지별 테스트
- «감사관» 역할도 설정했습니다: 원 프로젝트에서 과거를 조사하여 «원본에서 이미 죽은 코드»를 찾아내어 버그를 함께 유산으로 가져오는 것을 방지합니다

가장 기적같은 것은 마무리 단계의 저장소 전환입니다. 저는 여전히 «로컬 병합, 푸시, CI»의 클래식 프로세스를 떠올리고 있었는데, 바로 **클라우드로의 전환**이 왔습니다: 새로운 커밋 기록을 강제로 외부 `main`으로 푸시하고, 로컬 저장소를 `fetch + reset`으로 가져옵니다. Git Graph를 열어보니—어? 왜 여전히 오래된 기록이야? 거기서 속임수를 당한 줄 알았습니다. `git fetch`를 한 번 실행하면 세상이 조용해집니다:

- `main` = 새로운 StyleX 버전 (19번의 커밋)
- `archive/tailwind-v4` = 오래된 버전의 모든 기록, 같은 저장소에 보관된 안전장치
- 회복 방법: 한 번의 명령으로 롤백 가능

**가치가 있다면**, 당신은 스타일과 크기가 민감하고, 프로젝트가 장기적으로 유지보수가 필요하며, TypeScript를 많이 사용하고, 시간이 있다면 (가장 중요한 점입니다).

**조금 더 여유를 가지면**, 당신은 Tailwind 생태계의 구성 요소에 크게 의존하고 (shadcn과 같은 것들을 바로 사용할 수 있음), 프로젝트가 납품에 임박해 있거나, 단지 작은 사이트를 만들고 싶다면.

저에게는 가치가 있습니다 — 단지 38%의 비용을 절약하는 것만이 아니라, 앞으로는 "스타일이 잘못 입력되어도 오류가 발생하지 않는다", "주석에 있는 클래스명이 결과물에 포함된다", "이 CSS는 과연 누가 사용하고 있는가"와 같은 유령 문제를 다시 만나지 않을 것입니다. 스타일이 마침내 **유형이 되고, 소유자가 되고, 삭제 가능한** 일류 항목이 되었습니다.

> 97.7 KB → 60.3 KB.
> 133개의 파일, 19번의 커밍دمент, 0개의 사용자가 알아차릴 수 있는 변화.
