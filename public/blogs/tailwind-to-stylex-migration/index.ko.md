먼저 결론부터 말하자면, 이번에 전체 블로그의 스타일 체계를 Tailwind에서 StyleX로 바꿨습니다. 21개의 라우트, 133개의 파일 변경, 19번의 커밍دم. 메인 스타일 시트는 97.7KB에서 60.3KB로 (-38%) 줄어들었으며, 빌드와 실행 과정은 거의 변하지 않았습니다.

**전체 블로그의 모습은 이렇습니다——마이그레이션 전과 똑같습니다.**

완벽한 일치가 바로 이번 마이그레이션의 가장 큰 성공입니다.

## 왜 잘 작동하는 Tailwind을 버리나요?

먼저 정당성을 증명하자: Tailwind은 나를 해치지 않았다. 매우 유용해서, 클래스 이름과 문자열을 JSX 위에 붙이기만 하면 30분 만에 페이지를 만들 수 있다. 내 블로그는 바로 이 툴로 성장했다.

하지만 나는 StyleX에 대한 기대가 오래전부터 있었습니다—그것은 독특한 방식이 아닌 Meta의 제품입니다: 2020년에 Facebook 내부에서 시작되었고, 2023년 말에 오픈소스로 공개되었으며, Instagram과 WhatsApp의 생산 환경에서 5년 동안 사용되었습니다. 그것과 Tailwind은 두 가지 다른 철학입니다:

- **Tailwind 是字符串艺术**：`className="flex gap-2 px-4"`，所见即所得，但拼错了没人告诉你——样式只是「悄悄不生效」
- **StyleX 是 TypeScript 对象**：`stylex.create({ ... })`，写错属性名、放错值，`tsc` 当场把错误糊你脸上

저에게 가장 감동적인 세 가지:

1. **타입 안전성**：스타일이 처음으로 타입 시스템에 참여하면, 철자 오류가 «무반응»에서 «컴파일 에러»로 바뀝니다.  
2. **확실성**：Tailwind은 스캐너를 이용해 «어떤 클래스가 사용되었는지»를 추측합니다—이 부분은 많은 미스터리가 있습니다(템플릿 문자열로 생성된 클래스명은 스캔되지 않고, 주석에 클래스명을 적으면 오히려 결과물에 포함됩니다); StyleX는 컴파일러가 «어떤 스타일이 참조되었는지»를 알기 때문에 추측 없이 미스터리가 없습니다.  
3. **체중**：실제로 참조된 원자 클래스만 생성하며, 한 값에 전체 사이트에서 한 클래스를 사용합니다.

물론 더 단순한 이유도 있습니다: 블로그는 제 실험장입니다. 땅에 내지 않고 회사 프로젝트를 사용한다면 어떻게 될까요?

추가로 StyleX의 원리에 대해 말하자면, 실제로 매우 간단합니다: TS 객체를 작성하면 컴파일 단계에서 이를 **가장 세분화된 CSS 원자 클래스**로 분해합니다(한 클래스는 한 속성만 처리합니다). 실행 시에는 테이블 검색이 됩니다. **실행 시 스타일 주입이 없습니다**—CSS는 빌드 단계에서 이미 생성되어 JS에 아무 부담도 주지 않습니다. 실행 비용이 없고, 원자 클래스이며, 타입 안전성이 있어, 이 세 가지가 합쳐져서 완성됩니다.

## 전략: 먼저 함께 사용하고, 나중에 분리합니다.

100개 이상의 파일을 하룻밤에 바꿀 수는 없으니, 나는 「이중 라인 구조」 전략을 사용하고 있다.

**1단계: 두 프레임워크가 평화롭게 공존합니다.** Tailwind과 StyleX가 동시에 설치되며, CSS의 `@layer`를 이용해 순서를 정한다:

```css
@layer theme, base, components, priority1, ..., priority9, utilities;
```

StyleX의 아том 클래스가 중간에 위치하며 (priority1-9은 그들의 영역), 기존 컴포넌트는 여전히 Tailwind을 사용하고, 새로운 컴포넌트는 StyleX를 사용하여 각자의 역할을 수행한다.

**2단계: 디렉터리별로 파일을 분할하여 이동합니다.** 133개의 파일을 7개의 단계로 나누어, 각 단계마다 디렉터리 하나씩 이동하고, 각 단계를 완료하면 바로 검수를 진행합니다: 유형 확인 + 생산 구축 + 브라우저를 이용한 페이지 단계별 테스트.

**3단계: 마무리.** 모든 파일을 이동한 후의 어느 날 새벽에 Tailwind의 5개 의존성을 삭제하고, 모든 커스텀 도구를 정리한 후 작업을 종료합니다. 그 다음은 아래 다섯 가지 문제에 대한 이야기입니다.

## 문제 기록 (다섯 가지를 선별)

### 문제 1: `@stylex;` 명령어가 Tailwind에 의해 완전히 삭제되었습니다.

StyleX의 구축에는 마법적인 지시가 필요합니다: CSS에 `@stylex;` 한 줄을 작성하면 됩니다.

이상한 일이 발생했습니다: 설정은 완벽하고 구축도 성공적이지만 결과물에는 **하나의 원소 클래스도 없습니다**. 90분 동안 조사했지만, 결국 CSS 인터페이스의 컴파일 과정을 출력하여 단계별로 비교한 끝에 진실을 찾았습니다.

Turbopack은 각 CSS 인터페이스에 대해 **개별적으로** PostCSS 플러그인 체인을 실행합니다. Tailwind은 파일을 처리할 때 전체 파일을 "다시 컴파일"하므로, 이 과정에서 기반 컴파일러는 알지 못하는 `@stylex;`를 쓰레기로 처리합니다. 지시문이 자신만의 파일에 작성되든 import된 파일에 포함되든 피할 수 없습니다.

**해결 방법**: `@stylex;`을 독립적인 작은 CSS 인터페이스에 넣으세요. 이 파일은 Tailwind과는 전혀 상관없이, 지시문은 해당 파일을 처리하는 플러그인에게 전달됩니다.

### 坑二: 두 출처의 stylex 클래스명을 사용할 때 절대로 cn()로 조합하지 마세요.

이것은 실험 및 빌드 결과를 통한 두 가지 증거입니다.

StyleX의 합성 의미는 명확합니다 — **동일한 `stylex.props()`에서 뒤에 있는 값이 앞에 있는 값을 덮는** 방식으로, 덮인 애노틱 클래스는 출력에서 직접 제거됩니다.

하지만! 두 출처의 stylex 클래스명을 `cn()` 문자열로 조합하면 충돌이 "사전 순서"에 따라 해결됩니다 — `padding: 12px`가 `padding: 24px`로 처리되며, 당신이 정한 순서는 전혀 중요하지 않습니다.

**철률**：의미를 커버하는 경우 `stylex.props()`를 반드시 같은 방식으로 사용해야 합니다. `cn()`는 외부 클래스의 값을 전달하는 데만 사용됩니다.

### 공산삼：group-hover는 어떻게 처리하나요? marker가 해결책입니다.

Tailwind에는 `group-hover:`라는 강력한 기능이 있습니다. 부모 요소를 마우스 오버하면 자식 요소가 연동됩니다. StyleX에는 조상 선택자가 없는데, 이를 어떻게 처리할까요?

답은 StyleX의 marker 메커니즘입니다.

```ts
// 1. 마커를 정의합니다
export const hoverGroup = stylex.defineMarker()

// 2. 컨테이너에 마커를 추가하여 기존 'group' 클래스를 대체합니다
<div {...stylex.props(styles.wrap, hoverGroup)}>

// 3. 조건 스타일을 사용하여 하위 요소에 스타일을 적용합니다
const styles = stylex.create({
  overlay: {
    opacity: {
      default: 0,
      [stylex.when.ancestor(':hover', hoverGroup)]: 1,
    },
  },
})
```

컴파일된 핵심 규칙은 대략 다음과 같습니다:

```css
/* 마커가 있는 가장 가까운 조상에 마우스를 올렸을 때 마스킹이 나타납니다 */
.overlay:where(.marker:hover *) { opacity: 1; }
```

**의미와 Tailwind의 group-hover는 완벽하게 일치합니다**——가장 가까운 마커 조상을 인식하며, 목록에 있는 카드에 마우스를 올렸을 때 같은 레벨의 다른 카드에 영향을 주지 않습니다.

추가적인 놀라운 발견도 있었습니다: 원본 프로젝트의 감사에서 확인한 바에 따르면, **여러 곳에서 group-hover가 사실은 죽은 코드였습니다** (스타일을 적용하는 하위 요소가 group 컨테이너 안에 없어서 출시 첫날부터 아무런 효과도 없었습니다). 마이그레이션할 때 간단히 "悬停 효과 조사"를 했고, 죽은 코드들은 처리했으며, 원래대로 보존했습니다.

### 쓰레기 네: Tailwind을 분리할 때, 기반도 함께 사라졌습니다

이것이 가장 위험한 부분입니다.

Tailwind은 화면 가득한 도구들 외에도, 전체 사이트에 **preflight**라는 층을 숨겨서 추가했습니다: `box-sizing: border-box`, 링크 색상의 상속, 폼 폰트의 상속, 이미지의 `display: block` 등… 모두 "당신은 느끼지 못하지만, 제거하면 문제가 생기는" 종류의 것들입니다.

그날 밤 모든 것이 정상적으로 작동했습니다. 다음 날 점검할 때야 블로그 목록의 제목이 **브라우저의 기본 파란색 하이퍼링크**로 변경된 것을 발견했습니다. 다시 확인해보니 전체 사이트의 `box-sizing`도 조용히 `content-box`로 돌아왔습니다.

이러한 회귀는 눈으로 스크린샷을 보아도 전혀 알 수 없습니다 (대부분의 컴포넌트 스타일은 명확하게 표시됩니다). 이는 오래된 버전과 새로운 버전을 **요소별 비교 계산**을 통해 발견한 것입니다. 수정 방법은 Tailwind v4의 preflight 소스 코드를 한 줄 한 줄 이식하여 Tailwind의 사적 함수만 교체하는 것입니다.

교훈: **무언가를 분해하기 전에 먼저 물어보세요 – 그 외에 표면적인 기능 외에 무엇을 제공하는지도 알아야 합니다.**

### 장애물 5: 한쪽은 밝고 다른 한쪽은 어둡다, 두 가지 유형의 유령 클래스명

- **명의**: Tailwind의 스캐너는 **주석 내**의 클래스명을 진짜로 인정하여 CSS를 생성합니다. 마이그레이션 후 이 클래스는 완전히 해결되었으며, StyleX는 주석을 읽지 않습니다.
- **암의**: 특정 효과 컴포넌트의 텍스트 레이어는 실행 시 `document.createElement`으로 동적으로 클래스명을 부여하는 부분(JSX에 없음)이며, 모든 정적 스캐너에서는 보이지 않습니다. Tailwind을 분리한 후 이 두 클래스명은 "정의되지 않은 공백"이 되고, 마지막으로 "실행 시 클래스명 할당" 모드로 전체 라이브러리를 스캔해야만 나타나며, 이로 인해 변경되었습니다.

하나는 노출된 부정 보고, 다른 하나는 숨겨진 누락 보고——스캐너 방식 방안의 두 가지 고전적인 단점이 이번에 해결되었습니다.

## 성적표 (정직 버전)

| 지표 | 마이그레이션 전 | 마이그레이션 후 | 변화 |
|---|---|---|---|
| 주 CSS (raw) | 97.7 KB | 60.3 KB | **-38.3%** |
| 전송량 (gzip / brotli) | 17.8 / 14.5 KB | 14.9 / 12.9 KB | -16% / -11% |
| 첫 화면 JS | 1246 KB | 1256 KB | +0.8% (거의 변동 없음) |
| 빌드 시간 | ~4s | ~4s | 변동 없음 |
| 실행 시 지표 | — | — | 변동 없음 |

잠깐, 왜 raw의 용량이 38% 감소했는데 전송량은 10~16%만 감소했나요?

왜냐하면 **압축기와 원자 데이터는 ‘대체 관계’이지 중첩 관계가 아니기 때문입니다**:

- Tailwind의 결과물은 중복률이 매우 높아서 gzip/brotli가 대부분의 중복 데이터를 처리할 수 있습니다(압축 비율 6.8배)
- StyleX의 원자 테이블은 컴파일 단계에서 이미 중복을 처리했기 때문에 남은 내용의 ‘엔트로피’가 더 높아서 압축기가 처리할 것이 거의 없습니다(4.7배)

그러므로 raw -38%는 ‘스타일 엔진의 효율 향상’에 대한 정직한 수치이며, 전송 -10~16%는 ‘사용자가 실제로 절약한 트래픽’입니다. 두 측정 기준을 별도로 설명해야 합니다 – **마이그레이션은 점수 경기가 아닙니다. raw 수치를 가지고 전송을 과장하지 마세요.**

보이지 않는 곳에 진짜 이익이 숨겨져 있습니다: 약한 네트워크와 저급 기기에서 CSS 파일 크기가 37 KB 줄어들면 해석 및 메모리 사용이 수십 마이크로초 절약됩니다; 그리고——**결정성**도 있습니다.

이번 마이그레이션에는 재미있는 실행 방식이 있습니다: 저는 133개의 파일을 한 줄 한 줄 손으로 작성하지 않았으며, 대신 "총지휘자" 역할을 했습니다.

가장 기적같은 것은 마무리 단계의 저장소 전환입니다. 저는 "로컬 병합, 푸시, CI"의 클래식 프로세스를 머릿속에서 상상하고 있었는데, 그것이 바로 **클라우드에서의 혁신**이었습니다: 새로운 커밋 기록을 강제로 원격의 `main`으로 푸시하고, 로컬 저장소를 `fetch + reset`으로 가져옵니다. Git Graph를 열어보니—어? 여전히 오래된 기록이네요? 거기서 속임수를 당한 줄 알았습니다. `git fetch`를 한 번 실행하면 세상이 조용해집니다:

- `main` = 새로운 StyleX 버전 (19번의 커밋)
- `archive/tailwind-v4` = 기존 버전의 모든 기록, 같은 저장소에 보관된 안전장치
- 회복 방법: 한 번의 명령으로 롤백 가능

## 가치가 있을까?

같은 방식을 따라 하고 싶은 사람들에게 정직한 목록을 제공합니다:
